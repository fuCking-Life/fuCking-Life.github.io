1Silero VAD v6.3：短停顿和短语音更好检，端点中位延迟从 64 ms 降到接近 0

话轮控制端上语音开源发布

来源：GitHub snakers4/silero-vad。被广泛使用的端上 VAD（关注账号窗口内没有相关发帖）。。发帖日期：2026-11-23（新加坡时间 17:19 发布）。

Silero 正式发布 v6.3，提供新的 16 kHz 和 8 kHz 模型，文件名、输入输出和 API 不变，可直接替换。发布说明写：160–256 ms 的句内停顿检出率从 82% 提到 91%，96–128 ms 从 38% 提到 62%；长音频上的上下文保持更好；语音结束检测的中位延迟从 64 ms 降到接近 0；在同等虚警率下，非语音误触发更少、语音召回不变。同一阈值下 v6.3 比 v6.2 略严，若沿用旧阈值需要重测。silero_vad.onnx 重导出后图更简单（If 节点 25→1，总节点 689→163），opset 16 不变，可直接被 OpenVINO 加载；silero_vad_16k_op15.onnx 已没有 If。顺带修了 max_speech_duration_s 强制切分时后续语音被丢掉（#813），以及 speech_pad_ms 较大时 VADIterator 片段重叠（#818）。我没有在车载或 iPhone 上复测这些数字。

对 Luna 的启发 把现有 Silero 换成 v6.3 同名 ONNX 后，先不要沿用 v6.2 的阈值。重点回归车里 100–250 ms 的换气会不会被切成两句，以及“停”“出口”这类短指令会不会漏检。端点尾巴更短，有利于压 barge-in 和 end-of-turn；同时看路噪下误触发是否变化。图更简单，Core ML / ONNX Runtime 的加载和实时性也要一起测。

2Duopra：全双工模型边说边静默调工具，任务成功率从 4.7% 提到 44.7%

前沿语音模型话轮控制语音 agent 工程

来源：@zhangzhuosheng Zhuosheng Zhang。上海交通大学，Duopra 通讯作者（论文合作方还包括腾讯、上海大学）。。发帖日期：2026-11-23（新加坡时间 11:03 发帖；论文于 11-19 17:09 挂到 arXiv，只标注 cs.AI，日常检索未覆盖，昨日报告未写）。

作者线程宣布 Duopra：一个全双工语音模型，在说话的同时决定是否行动。工具调用走不发声的私有通道，可以把后端 agent 当作 query(task) 这一类工具来委派，也能在用户改口时用更新后的参数直接调域工具。他们把问题分成会话代理和任务代理：Realtime-Venus-Audio + Harness 在流式流水线、Full-Duplex-Bench v3 上只有 11% 的会话把请求交到后端，Pass@1 仅 4.7%；其余 89% 里后端根本没接到任务，其中不少已经开口却从未发起工具。换成 Duopra、后端仍是 Qwen3-8B 时，Pass@1 升到 44.7%；自己直接调工具为 47.7%（SFT 后 26.0%，全双工 RL 后再升到此值），接 DeepSeek 后端为 49.3%（各 300 个会话）。在 Full-Duplex-Bench v1.0 上，句中停顿误插入从基模 18.1% 降到 5.4%，用户打断后的响应从 79.5% 升到 91.3%。训练分三步：在 12,800 段合成对话上做协议 SFT、用及时且完整的执行做全双工 RL，再只调 speech projector。这是 GPU 上的 speech-to-speech，不是端上小模型。我读了摘要、项目页和作者线程，没有跑演示，也没有逐节核对正文实验设定。

对 Luna 的启发 不必把级联换成双工基座，但应单独测“任务有没有真正发出去”，不要只看助手有没有开口。司机中途改目的地或数量时，只把最终参数交给导航工具，不要先按旧值下单。函数名不要读出来，调用走静默通道。评测可对照 Full-Duplex-Bench v3，端上的延迟、回声和电池要另测。

4sherpa-onnx：流式 NeMo CTC 把子采样写死成 4，1.2 s 端点实际要约 2.4 s，还会吃掉下一句首词

话轮控制端上语音

来源：GitHub k2-fsa/sherpa-onnx。Next-gen Kaldi 的端上语音运行时（关注账号 @csukuangfj 窗口内没有发帖）。。发帖日期：2026-11-23（新加坡时间 11:35 合并 PR #4282；尚未打进正式版，当前标签仍是昨日的 v2.0.3）。

PR #4282 修的是流式 CTC 的端点与时间戳。OnlineRecognizerCtcImpl 对除 T-one 外的流式 CTC 都按子采样因子 4 来算 IsEndpoint() 和 GetResult()，而流式 NeMo FastConformer CTC 的元数据是 8，运行时其实已经读到了这个值。于是尾静音被算成一半长：规则 2（1.2 s）大约要 2.4 s 才触发，复位后又常丢掉下一句第一个词；token 时间戳也被折半（作者在 6.6 s 的 0.wav 上看到末词 3.2 s，同款 NeMo transducer 则是 6.4 s）。修复后改为读取模型的 SubsamplingFactor()，其他 CTC 默认仍为 4。作者用 sherpa-onnx-nemo-streaming-fast-conformer-ctc-en-80ms-int8、40 路流、5 条 LibriSpeech、间隔 1.0–2.5 s 的 −65 dBFS 噪声、默认端点规则、0.1 s 块做了回归：test-clean WER 4.80%→3.22%，端点后首词错误 29.6%→4.4%，test-other WER 9.75%→8.84%。我没有在 iOS 上复测。同日还合并了说话人日志里按流设置 min_duration_on / min_duration_off / window_shift_ratio（#4255），是昨日聚类修复的后续。

对 Luna 的启发 若流式 ASR 使用 NeMo CTC 或任何子采样不是 4 的模型，端点和时间戳必须用模型元数据里的因子，不要写死。否则看起来是 1.2 s 的 end-of-turn，实际会拖到约 2.4 s，下一句开头还可能被吃掉。换模型家族后，要用“短句 + 1–2 s 间隔 + 噪声”专门看首词错误率，不要只看整段 WER。这笔修复还没进正式发布包。

5Sophon Realtime 1.6.2：say 不再因 token 余量不够念到一半，通话开始、对方未开口也能播

话轮控制语音 agent 工程前沿语音模型

来源：GitHub adventists-ai/sophon-realtime。开源实时 speech-to-speech 引擎，带 OpenAI Realtime 兼容面以及 LiveKit / Pipecat 网关。。发帖日期：2026-11-23（新加坡时间 20:54 发布）。

这是昨日 v1.6.0 / 1.6.1 的后续。v1.6.2 修了两处 say 行为。一是句子可能在结束前被截断：原先 token 上限是“常规分词长度 + 16”，约束解码会把同样的字拆成更多短 token，4B 上长回读会在上限处停住；现在改为“UTF-8 字节数 + 8”（每个 token 至少对应一个字节，句子总能放下）。若 say 被呼叫方打断或因其他原因提前停，历史和日志只保留实际播出的字，并记下停止原因。二是在对方还没开口时发送的 say 原先无效（例如通话一开始的录音提示），因为工具桥的 key 要等到第一轮回复才建立；现在引擎启动就打开桥，尚未注册的会话会排队，并被要求注册（一次一次性的 turn question）。作者在 Flash 4B、经 Live 网关验证：8 段长回读（姓名、数字、地址，含一句中文）× 3 轮都念完，且每段会话的第一句 say 都在任何语音之前发出。插件版本升到 1.6.2，Live 网关本身没有改。这仍是服务端 / GPU 上的模型，不是端上权重更新。

对 Luna 的启发 导航回读、录音提示这类“按原文朗读”不要用“token 数 + 固定余量”当停止条件，量化或约束解码可能把同一句话拆得更碎，会念到一半被切断。被打断时，对话历史只留实际播出的字。安全声明或录音提示必须在司机开口前就能播，不要等第一轮用户语音才打开通道。

6Hugging Face speech-to-speech：把确认语和工具调用拆成两条 assistant 消息后，后续轮次会只说不做

语音 agent 工程开源发布

来源：GitHub huggingface/speech-to-speech。可替换模块的级联语音管线（关注账号 @andimarafioti 窗口内没有相关技术帖）。。发帖日期：2026-11-23（新加坡时间 23:15 合并 PR #664；同日 23:24 合并配套评测 #868）。

PR #664 修的是历史写法。一句“我来帮你设 20 分钟米饭计时”再说 set_timer，在 Realtime 缓冲里是一条 assistant 文本加一条 function_call；转成 Chat Completions / transformers 模板后变成两条 assistant 消息，模板会在第一句末尾就关闭回合。模型学会这个形状后，后续请求往往只说引导语、不再发出调用。作者在 Qwen3-VL-30B-A3B-Instruct-FP8、vLLM、与线上相同的语音系统提示和工具下，用一轮“先说再调”的历史接 6 类后续工具请求、各 16 次：拆成两条时 0/96 调对工具，合并成一条同时带 content 和 tool_calls 后 96/96。同日 #868 加了 tool_conversations 评测，用脚本化多轮对话经 Realtime 服务器跑通，用来固定测量历史、提示词和后端的改动。这是服务端级联管线的修复，不是新模型。

对 Luna 的启发 确认语和这次工具调用必须写在同一条助手消息里。若先存“我来帮你查加油站”、再另开一条只放函数调用，后面几轮很容易只开口、不再调工具。加一条回归：第一轮工具成功之后，紧接着再下一轮指令，工具仍要发出。

7LiveKit Agents：未完成的 function call 不要修补后执行，半截 JSON 会被当成成功

语音 agent 工程

来源：GitHub livekit/agents。开源语音 agent 框架（关注账号 @livekit 窗口内没有发帖）。。发帖日期：2026-11-23（新加坡时间 11:18 合并 PR #8703）。

PR #8703 修的是 OpenAI Responses 流。当模型还在写工具参数就撞上 max_output_tokens 时，服务端会以 status: "incomplete" 结束该 function_call，再发 response.incomplete。旧逻辑在看到 output_item.done 时不管 status 就把调用放进 function_ch，工具执行是并发的，报错来不及拦住。parse_function_arguments 还会修补截断 JSON，作者举的例子是意图为 21 的 {"temperature": 2 被修成 2，工具带着错误值跑完，还被记成成功调用。修复后：status 已设置且不是 completed 的调用不再派发。这是此前 GPT Live 后端已有的规则，现在落到共用的 Responses 引擎，覆盖 WebSocket / HTTP 以及 Azure、xAI 等子类。没有 status 的条目仍会派发，以免兼容提供商被误伤。仓库尚未为此打新版本号。我没有在真机上复现。

对 Luna 的启发 工具参数若是流式生成的，响应一旦是 incomplete，就不要把半截 JSON 修补后执行，更不要记成成功。宁可报错或重试，也不要把“21 度 / 21 号出口”做成 2。只有 status 为 completed，或你们明确知道该提供商根本不返回 status 时，才真正调导航或拨号。

原帖：修复 · 代码

9MaAI-Synth：用 LLM 脚本 + TTS + 独立时序模型合成带话轮、重叠和 backchannel 的双轨对话（稍早于本窗口）

话轮控制开源发布

来源：@inokoj Koji Inoue（井上昂治）。京都大学，MaAI 对话时序模型作者。本窗口关键词检索到对此仓库的引用；原帖在今日窗口开始前约 50 分钟（11-23 07:52），落在昨日窗口内但昨日报告未写，故标明稍早并补记。。发帖日期：2026-11-23（新加坡时间 07:52 发帖；仓库 11-22 创建，窗口内 14:58 仍有推送）。

京都大学开源 MaAI-Synth：一条从情景设计到立体声音频的口语对话合成流水线。LLM 写场景和剧本（保留语气词、句末助词和短轮，并经质量门），音色克隆 TTS 按指定说话人读出每一句，再用 MaAI 决定每句何时开始、附和插在何处，避免变成轮流朗读。输出为分轨音频（ch0 系统、ch1 用户）和带时间对齐的转写，可直接用作全双工训练数据。默认组合是 Gemma 4 31B + Irodori-TTS-v4.1-Small-Yomi + MaAI；示例音色是 Inoue 与 Mori。README 给出七类情景（初次见面、长停顿、倾听附和、重叠抢话、问答等）共 35 段样本，并标明 2026 年 11 月为首个公开版本。现成样本和默认 TTS 偏日语。我读了仓库说明和项目页，没有听完全部样本。

对 Luna 的启发 训或评 end-of-turn、backchannel 和重叠时，不要只用轮流朗读的对白。可以借鉴这套拆法：剧本保留短轮和语气词，另用时序模型决定开口和附和，并保存分轨与对齐转写。现成样本不能直接当中英车载数据，但“长停顿 / 附和 / 抢话”这些情景可以用来录司机数据。

来源：@tarush_agarwal_ Tarush Agarwal。Cekura CEO。引用的是 11-19 已发布的 GPT-Live-1.1（不在本窗口），今日新的是这份真人电话评测。。发帖日期：2026-11-23（新加坡时间 20:39）。

Tarush 写：GPT-Live 1.1 + GPT-6 Sol 在 Cekura 的 Real Human Calls 上为 16 个模型中的第 1，1187 ELO；Grok Voice 3.0 为 1158，GPT-Live 1 为 1123。与此次发布最相关的技能上，超过 70 通录制电话、各跑三轮，它也是第一：人名、数字和日期抓取 83%（下一是 GPT-Live 1 的 76%）；风格要求遵循 82%（下一是 Grok Voice Think Fast 2.0 的 78%）；三轮都处理得好的来电者比例 46%（下一是 Grok Voice 3.0 的 43%）。中位回复 1.86 s，低于同设置下 GPT-Live 1 的 2.27 s。这是云端全双工 API 的第三方评测，我没有复跑，也没有完整转写配图。

对 Luna 的启发 云端 GPT-Live 不是 Luna 的主路径，但“人名、数字、日期”应单独打分。导航里的出口编号、公里数、ETA 和地名同音字要比闲聊更严。他们的中位回复 1.86 s 对车机仍偏慢，端上要以开始出声为准另测。

11CopilotKit 上线 A2UI Playground：智能体写出 A2UI 1.0，由本机组件目录渲染

agent 与界面

来源：@CopilotKit CopilotKit 官方。开源 agent 前端框架，也是 AG-UI 的维护方。。发帖日期：2026-11-23（新加坡时间 21:14）。

CopilotKit 宣布推出 A2UI Playground，并说被 Google 转发介绍。我打开了 https://a2ui.open.bot/ ：页面说明“向智能体要一个界面，模型写出 Google 的开放协议 A2UI，再由你的设计系统画出来”；可选用 CopilotKit 标准目录、shadcn/ui 或自定义组件，也可以不经过模型、手写 A2UI JSON。示例是按地区的销售看板、按套餐的注册量等仪表盘。Google 当日较早的介绍帖还提到 A2UI 1.0 提供开源 SDK 和双向 function call，把 agent 意图绑到组件上。我没有在 playground 里实际跑一轮生成。同日 @ataiiam 主要是 AG-UI 安装量和 OpenBot 的推广，没有新的协议变更，未另列。

对 Luna 的启发 可以用这个 playground 看“意图如何写成组件、再由本机设计系统渲染”。导航里的路线卡片或加油站列表，仍应优先走已有的 function tools / App Intents 画原生 UI，不要把 Web 组件嵌进驾驶视图。协议本身可以继续跟。

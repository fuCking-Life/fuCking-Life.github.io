1audio.cpp v0.9.6：用 ggml 原生跑起 Inworld Voice Isolator，实时隔离前景人声

端上语音开源发布唤醒与声纹

来源：@0xShug0 0xShugo。audio.cpp 作者，用 ggml 做本地音频推理。发帖日期：2026-11-22（新加坡时间 02:39；GitHub 正式版 v0.9.6 于 02:12 发布）。

@0xShug0 宣布 audio.cpp v0.9.6 接入 Inworld Voice Isolator（社区移植，PR #1343，作者 Etherll），用来从嘈杂音频里抽出前景人声，并附了一段演示视频；我没有复测视频里的效果。模型本身已在 11-19 开源（Apache-2.0）：离线约 64M、实时约 58M，48 kHz，官方说明它不是目标说话人选择器，也不做语音修复。audio.cpp 的移植把两套权重做成 F32 GGUF（实时约 233 MB、离线约 256 MB）；实时通路是因果流式，look-ahead 可选 0 / 2 / 4 帧，PR 写默认 2 帧时算法延迟约 62.7 ms；输入会先混合成单声道并重采样到 48 kHz。同版本还修了离线 Metal 投影溢出，并改进了流式复用和 WebUI / WebGPU。发布说明里对 Luna 较相关的还有：tiny-voca（4.5M 参数、自带音素器的英语 TTS）、可嵌入的静态 C API（libaudiocpp.a），以及 PocketTTS 的流式质量修复。框架本身是 C++ / ggml，支持 Windows / Linux / macOS 与 CPU、CUDA、Metal、Vulkan、HIP；我没有看到官方 iOS SDK。

对 Luna 的启发 可以把实时隔离放在车载 VAD / 流式 ASR 前面，先压路噪、导航播报残留和车内嘈杂，再交给端点判断。它不会“只听司机”：副驾或后排说话仍可能被当成前景，定向唤醒和声纹还得另做。先在 Mac 上用实时 checkpoint 录导航加路噪，看误触发和 ASR WER，再决定是否用 C API 静态库往 iOS 迁；不要用演示视频代替车内实测。

2llama.cpp 把 Kyutai Hibiki 接进服务端全双工实时通路（目前是法英同传，不是通用助手）

前沿语音模型开源发布话轮控制

来源：GitHub ggml-org/llama.cpp PR #32491，作者 ngxson（Xuan-Son Nguyen，Hugging Face 工程师，llama.cpp 多模态主要贡献者）。发帖日期：2026-11-21（新加坡时间 21:25 合并；夜间版 b12619 于 11-22 07:45 发布）。

ngxson 向 llama.cpp 合并了 Kyutai Hibiki 的 mtmd 支持，目标权重是 Hugging Face 上的 hibiki-1b / hibiki-2b（PyTorch bf16）。模型卡写明：Hibiki 是流式语音同传，用 Moshi 的多流架构同时建模源语言和目标语言语音，当前只支持法语到英语；1B 这档在论文里称为 Hibiki-M（面向移动端），约 1.7B 参数，按 12.5 Hz 同时给出文本和语音 token，许可是 CC-BY。PR 说明这次顺手在 server 加了全双工，而且“目前只在 server 实现，供后续模型复用”。评审 ServeurpersoCom 的说法是：实时端点里第一段音频打开回复，80 ms 进、80 ms 出，客户端不再做话轮逻辑；他在 CUDA 上用 Hibiki-1B 测过一段约 26 秒、由 Qwen3-TTS 合成的法语材料。这不是 iOS 端上的通用全双工助手，我也没有在 Apple Silicon 上复测。

对 Luna 的启发 不要把 Hibiki 直接接到司机助手：它是法英同传，不是导航里的对话和工具调用。值得看的是 llama.cpp 这条“固定帧率、听和说同时走、客户端不做话轮”的服务端协议，以及 1.7B 档曾被作者标成移动端。Luna 仍应坚持级联；若以后要在本地试 Moshi 类双工，先认清这次落地只在 server，车机和 iPhone 上的延迟、回声消除都要另测。

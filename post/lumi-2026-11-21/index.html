话轮控制论文语音 agent 工程

来源：arXiv 2611.25489 Ahmet Tuğrul Bayrak、Fatma Nur Korkmaz、Mustafa Sertaç Türkel、Nur Yağmur Tuncer。发帖日期：2026-11-19（新加坡时间；11-19 12:26 提交，昨日报告未收录）。

我读了摘要和 arXiv 摘要页（未读全文 PDF）。作者指出：语音 agent 若只等一段固定静音再开口，要么会打断还在停顿的用户，要么对已经说完的人反应太晚。他们在 Real-TurnTurk（土耳其语双人视频通话）里取出话轮结束和话轮内部停顿，比较微调的土耳其语 TurnGPT、零样本土耳其语语言模型、一套已部署的多语种检测器，以及语音活动时序和面部特征，并做了按录音划分和按说话人划分的评估，以及成对 cluster bootstrap。在留出录音上，微调模型对“说完 / 只是停顿”的区分好于两个文本基线，校准也是三个文本模型里最好的。当前说话人的时序特征同样有用；用逻辑回归把它和微调文本分数合在一起，是他们时序方案里最好的。在延迟仿真中，把文本分数加到静音超时上，能在同样的打断率下缩短平均回复延迟。自动 Whisper 转写上，微调模型相对零样本的优势仍然在。这是土耳其语语料上的研究，我没有复现。

对 Luna 的启发 Luna 不要只靠固定静音切话轮。车里司机常在报地名、门牌或等导航计算时中途停顿，应把端点文本分数（或小分类器）和 VAD 时序合在一起，并按“同样打断率下平均等多久”来调阈值。这项工作用的是土耳其语和当面视频通话，中文、车噪和只有音频、没有面部信号的条件要自己测。

话轮控制语音 agent 工程端上小模型

来源：pipecat-ai/pipecat 开源实时语音 agent 框架。窗口内 @pipecat_ai 没有发帖，内容来自我读取的已合并 PR。发帖日期：2026-11-21（新加坡时间；PR 于 11-21 04:55–06:38 合并，尚无新版本号）。

我读了 PR 正文（未自己跑代码）。#6587 指出：原来的用户空闲控制器只给机器人说完后的静音计时，并报 on_user_turn_idle，分不清用户无话可说，和用户在等一次异步函数调用或 LLMWithBackend 后台任务，结果空闲超时会在工具还在跑时触发。这次用 BackgroundWorkStartedFrame / BackgroundWorkFinishedFrame 标出不阻塞对话的后台工作；有后台工作时，静音改为“用户在等待”，到 user_waiting_timeout 后发出 on_user_waiting，空闲计时器此时不走。空闲和等待都同时变成事件和帧（UserTurnIdleFrame、UserWaitingFrame，带 quiet_secs）。#6588 加上 WaitReassuranceLLMExtension：在 UserWaitingFrame 上再跑一次 LLM，让模型用自己的声音说一句简短安抚，或用静默标记（默认 ∅）选择不开口；静默回复不会进入下游、观察者或上下文，但会重开等待间隔，好在长等待里再次决定。PR 写明：级联和异步工具示例会挂上该扩展；speech-to-speech 示例不用，因为静默回复无法从音频里读出。同批还有 LLM 扩展抽象（#6585，话轮完成是第一个扩展）和异步工具扩展（#6590）。#6913 修了评测：用户开口时 vad-user-started-speaking、user-started-speaking、bot-interrupted 会连续到达，原先每条打断报告都会清空队列，脚本若还在等前两个事件就会超时；现在打断时保留队列，同时仍丢掉机器人没说完的回复。

对 Luna 的启发 导航查路、改目的地或调用云端 LLM 时，不要把司机的沉默当成“可以继续催，或当作用户已离开”。先标出“工具在跑”，再决定是播一句很短的“我在查”还是保持安静；级联管线可以这样做，端到端语音模型则要另想信号。评测打断时，VAD 开始、用户开始说、机器人被打断这几条事件会挤在一起，不要用“后一条清空前一条”的队列，否则端点用例会误报超时。这些改动还没有进正式 release，合入后要再对一下版本。

话轮控制语音 agent 工程

来源：livekit/agents 窗口内无新 release 标签；内容来自我读取的已合并 PR。@livekit 本日另有 Expo 模板帖，与这两条 PR 不是同一条。发帖日期：2026-11-20（新加坡时间）。

我读了 PR 正文（未自己复测）。#8638 给 Gradium STT 插件加上 PREFLIGHT_TRANSCRIPT：服务器 VAD 第一次触发时，先把目前听到的词作为预览转发，LLM 用这份预览开请求，只有终稿和预览不同才再请求一次。作者写，按插件默认参数、对着真实 STT 模型的一次小基准，agent 开始说话大约早 350 ms，且没有多出额外的 LLM 调用；更激进的 VAD 可能带来多余请求，那时可以关掉抢跑生成。PR 还加了手动 flush。#8698 把 JS SDK 里修“幽灵 partial”的改动移植到 Python：Scribe v3 Live 的一条新 partial 若在本地 VAD 仍为静音时，会在配置的服务器静音阈值再加 0.5 秒后结束该话轮，避免一条一直不提交的 partial 无限期挡住 agent 回复。该保护只作用于“这条 partial 打开了一个新话轮”的情况；供应方提交、VAD 重新检测到语音、重连等会取消或重启它。#8633 则避免 error 帧直接丢掉上次 final 之后已缓存的词。这些都还没有打进新的 agents 版本号。

对 Luna 的启发 级联里也可以在 end-of-turn 定稿前，用“VAD 已触发、文本已较稳”的预览去预热意图 / 工具，终稿若只改了几个词就不必重跑；作者的 350 ms 是 Gradium 云端插件上的小数，不能当成车载数字。另一侧：流式 ASR 的 partial 若没有超时或 VAD 约束，会把 TTS 挂住，表现为司机说完了 Luna 却一直不答，需要给未提交的 partial 设上限。

语音 agent 工程话轮控制前沿语音模型

来源：@tarush_agarwal_ Cekura CEO。帖中只有一张图、没有数字。下面的数字来自我读取的公开榜单页，页面写 Last updated Nov 19, 2026。发帖日期：2026-11-21（新加坡时间；原帖 11-21 00:05。榜单页标注 11-19 更新，昨日报告未写该页）。

@tarush_agarwal_ 说比较了 15 个 speech-to-speech 模型的速度、可靠性和准确率，但推文本身没有给出数字。我打开了 https://benchmarks.cekura.ai/speech-to-speech/real-calls：15 个模型，用录好的真实来电做直播通话；合计 70 通（英语 55、西班牙语 7、印地语 8），银行和医疗各 35 通。每个用户会对每个模型各跑三次，Pass³ 是三次都处理好的比例；ELO 来自两两对战（均分 1000）；回复延迟 P50 是用户说完到 agent 开始回答的等待。我看到的前几名：Grok Voice 3.0，ELO 1161，Pass³ 43%，P50 1.60 s，话轮 81，任务完成率 73.8%，设置为 grok-voice-3.0、reasoning high、Service turn detection；GPT-Live 1 + GPT-6 Sol，ELO 1122，Pass³ 39%，P50 2.27 s，话轮只有 71（是它最弱的一项），任务完成率 79.0%；GPT Realtime 2.1，ELO 1091，Pass³ 26%，P50 2.16 s，endpointing 是明显短板；Gemini 3.1 Flash Live Preview 的 P50 是 3.06 s，设置写 Shared local turn detection；Azure Realtime 的 endpointing 只有 15 分（比平均低 46 分）。这些是云端 API、电话场景，我没有复跑。同一站点的 agent 表现榜更新于 11-3、turn-bench 更新于 10-13，不当作窗口内新结果。

对 Luna 的启发 这是电话云端模型的榜，1.6–3 秒的开口延迟不能当车载目标。值得抄的是指标拆法：把话轮、endpointing、任务完成、同一用户三次是否都稳定分开看，而不是只报一个延迟。GPT-Live 组合任务完成更高、话轮更弱，说明“像不像人接话”和“能不能把导航指令做对”要分开评。Luna 应自己做司机 + 车噪 + 中文短指令的同类拆分，而不是沿用这些云端名次。

端上小模型agent 与界面语音 agent 工程

来源：@_philschmid Philipp Schmid，Google DeepMind，负责 Agents 与 Gemini API。我读的是 X 长文的全文（article.plain_text），没有打开官方文档站（短链跳到了登录页）。发帖日期：2026-11-20（新加坡时间 23:52）。

文章写，Gemini API 预览了 Dynamic Tool Retrieval（Tool Search Tool）：agent 可以在后台挂着上百个工具，一开始只让模型看到短名称和一句话描述，需要时再加载完整参数 schema。作者认为每一轮都把 100 多个完整 schema 打进上下文既耗 token，也损害工具选择。两种模式：服务端在 tools 里加 {"type":"tool_search"}，并对函数或远程 MCP 设 defer_loading: true，模型先只看到约 26 个 token 的一行摘要（或更短的 short_description），检索和加载发生在同一次 API 请求内，前缀仍可缓存；客户端模式把 execution 设为 client，工具目录完全放在 tools[] 之外，可用向量检索或 Gemini Decision 1（gemini-decision-1，文中称零输出 token）打分后再把命中的 schema 塞回。建议把最常用的 3 到 5 个工具保持常驻、长尾再延迟加载；少于约 20 个工具时，静态加载仍然更简单。预览期初始化要带 apiVersion: "v1beta"；即使用 previous_interaction_id，每次仍要重发完整的 tools 数组。这是云端 Gemini 的能力，不是端上运行时。

对 Luna 的启发 导航 App 的 function tools 很容易超过小模型一轮能认真看完的数量。端上意图模型应只常驻高频工具（导航、限速、寻找停车、打电话），其余用短描述检索后再加载 schema，并明确本地 / 系统 / 云端分流。不要把云端“20 个工具以下不必检索”的经验直接当成 iPhone 上的预算，端上上下文更紧，阈值要自己测。

来源：@JonPTaylor Jon Taylor，Daily / Pipecat 语音 AI 工程师。我读了原帖和仓库 README。发帖日期：2026-11-20（新加坡时间 18:00；仓库同日 17:15 创建）。

他发了一段在灵动岛里做实时转写的演示，并问为什么 Apple 自己不提供。仓库 https://github.com/jptaylor/transcript-island 是 macOS 菜单栏应用：快捷键（默认 ⌥⇧Space）开始听写，字出现在岛/刘海长出的黑条里，结束后粘贴到刚才的输入框或剪贴板。README 写，语音识别完全在 Mac 上，使用 Apple 的 SpeechAnalyzer；需要 macOS 27 或更高、且支持端上语音识别的机器，以及 Xcode 27.2 才能编译。停约 2 秒会自己结束（Esc 立即结束）；PauseDetector 把识别器的新词、或明显高过环境底噪的电平当作有人在说，约 2 秒静音结束听写，若什么都没说则约 8 秒。这不是 iOS App，也不能直接用于车载免提。

前沿语音模型开源发布论文

来源：@kyutai_labs Kyutai。我读了他们的线程、arXiv 2611.26540 摘要、GitHub README 和 Hugging Face 模型说明。博客页 https://kyutai.org/blog/2026-11-20-aura/ 可以打开，但正文是前端渲染的，我没有在浏览器里看到全文，技术细节以摘要和 README 为准。发帖日期：2026-11-20（新加坡时间 23:06；论文提交于 11-20 02:17，属 cs.CV，昨日语音检索未覆盖。网站 last-modified 为 11-20 22:57 新加坡时间，昨日记录仍为 10-30）。

Kyutai 宣布 AURA，并把代码、权重和演示开源。论文与 README 写：模型按块生成说话头视频，每块只需要当前块的音频，不必向前看数秒；从 50 步双向 teacher 蒸馏成 4 步因果 student（先对齐 teacher 轨迹，再用 DMD），用滚动 KV cache 保持显存不随时长增长。AURA-1.3B 用 Mimi 作音频编码，输出 576p、16 fps，论文中在一块 H100 上端到端 20.7 fps（相对自己的 teacher 快 23 倍），许可 CC BY-NC 4.0；AURA-5B 输出 720p，论文中 9.7 fps（快 17 倍），许可是 Snap 非商用。仓库里的参考实现在加 --compile 后，同一块 H100 上大约是 1.3B 的 16 fps、5B 的 8 fps，和论文中的优化管线数字不同。演示把 AURA-1.3B 和他们的级联语音系统 Unmute 接在一起。还发布了 3 万条合成视频及 teacher 轨迹数据集。线程里对比的 Wan-S2V / Hallo3 等 fps 是作者给出的数字，我没有复测。这是单卡 GPU 上的视觉生成，不是端上语音模型。

对 Luna 的启发 不要在开车时把说话头像铺在导航屏上。有参考价值的是“按块、无未来音频、KV cache 恒定”的流式思路，以及演示里视觉模块挂在级联 Unmute 之外、而不是塞进语音模型。两套权重都是非商用许可，不能直接进产品。若以后要在停车态做数字人，也应按车机算力重测，不能沿用 H100 的 20.7 fps。

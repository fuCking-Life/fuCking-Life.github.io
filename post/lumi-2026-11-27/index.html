1μ-Bench：共享空间里的多人语音任务评测；专有系统最高 62.24%，开源全双工模型都在 20% 以下

话轮控制语音 agent 工程论文

来源：论文作者团队。通讯作者包括上海人工智能实验室的 Zhuan Shi、Jing Shao；作者来自上海交通大学、上海人工智能实验室、国科大、复旦、清华大学。仓库与项目页由 lqh1106/mu-bench 发布。关注名单中没有对应 X 账号，今日由 arXiv 检索得到。。发帖日期：2026-11-26（新加坡时间 02:58 提交；落在昨日窗口内，昨日报告未收录，今日从 arXiv 拉取并阅读）。

μ-Bench 评测共享空间里的全双工语音 agent：多个用户目标互相依赖，还要遵守每人的权限和隐私。论文的引入例子就是一家人去机场：家长要在 10:00 前到达，孩子中途插话要求绕路去公园，助手既要核对新路线是否误点，也要得到有权限的人同意。模拟用户按各自隔离的目标、知识和权限行动，并随助手的话和工具结果改口。20 个领域、100 个情景，按人数、声学和追问 2³ 展开成 800 个用例（408 个要调工具，392 个只靠说话）。主指标 Joint Task Success（JTS）要求所有用户目标、隐私边界和终态同时成立；Pure JTS 还禁止未授权的工具调用；Attribution / Threading / Coordination（ATC）分别看话是谁的、任务线有没有断、权限和公平有没有守住。我读了摘要、第 4.2 节主结果、Table 2 和第 5 节分析，也打开了项目页和 GitHub 仓库说明；没有跑评测，也没有收听项目页上 18 秒的示意图音频。Table 2（作者自报，我未复测）：无工具赛道上，专有系统 JTS 为 37.50%–62.24%，最高是 Grok Voice 3.0 的 62.24%，GPT-Realtime-2 为 58.42%，MOSS-Live 为 57.91%，Gemini 3.8 Live 为 53.32%，Seeduplex 3.0 为 37.50%；开源权重全部低于 20%，最高是 MiniCPM-o 4.5 的 19.39%，Moshi 为 1.79%，Freeze-Omni 为 0%。有工具赛道只测了四个专有系统，最高是 GPT-Realtime-2 的 65.44%，Gemini 3.8 Live 为 64.95%，Grok Voice 3.0 降到 57.60%，Seeduplex 3.0 为 50.00%。开源模型这一项的 Coordination 仍有 76%–87%，但 Threading 大多很低，作者的解释是：只盯着最近一句、把更早的任务线丢掉，反而较少泄露或越权，所以不能只看 Coordination。人数从 2–3 人增到 4–7 人时，能完成任务的系统 JTS 都下降：有工具的专有系统相对下降 19.64%–29.48%；无工具赛道上 MiniCPM-o 4.5 相对下降 47.98%。声学不流畅带来的相对变化大多在 8.8% 以内（Seeduplex 3.0 除外，同样是 −29.48%）。对 MiniCPM-o 4.5 的累计辅助实验里，先把重叠和打断改成轮流说话，JTS 从 19.39% 升到 26.79%（+7.40 个百分点，约占全部增益的六成以上）；再加上身份元数据和结构化语义，也只到 31.38%，仍有 68.62% 的会话没有完成。有工具的四个系统中，21.81%–71.81% 的用例出现了未授权工具调用（Seeduplex 3.0 最高），而且即便发生了一次未授权调用，条件 JTS 仍有 39.02%–61.64%。作者指出，工具框架往往相信模型自己申报的“是谁在请求”，没有做说话人核验。用户语音由 Fun-CosyVoice3-0.5B 合成，这是模拟评测，不是车内真人口语。

对 Luna 的启发 车里就是共享语音通道：司机设目的地和到达约束，乘客会插话改路或问无关的事。不要只评“能不能打断、会不会抢话”，还要单列：这句话是谁说的、任务线有没有被乘客插话打断、以及有没有在未确认司机同意时调用改路、打电话一类工具。函数工具必须带上说话人身份和权限，不能让模型自己填“请求人”。端上可以先做旁听和说话人标签（昨天的 Sidechat 正是这一层），再把重叠语音尽量收成带说话人的顺序转写；即便如此，多人目标冲突仍要单独做策略，不要指望全双工基座自己搞定。这套 800 例可以先作对照，但中文和车噪必须用自己的录音补测。

2sherpa-onnx：流式端点后可选择保留编码器状态，NeMo 流式模型首词错误从 6.9% 降到 3.8%

端上语音开源发布

来源：k2-fsa/sherpa-onnx。Luna 关注的端上流式 ASR / VAD / 唤醒仓库，由 @csukuangfj（Fangjun Kuang）等维护。本窗口没有对应 X 原创帖，变更来自已合并的 GitHub PR。。发帖日期：2026-11-26（新加坡时间 14:15 合并 PR #4305）。

合并的 PR #4305 关闭了 issue #4291。流式 CTC（T-one 除外）和 NeMo transducer 在端点后的 Reset() 默认仍会恢复编码器的初始状态；现在增加按流设置的选项：keep_encoder_states=1 时，Reset() 保留编码器状态。NeMo transducer 的 decoder 仍然会重置。作者用 40 路流、每路 5 条 LibriSpeech test-clean、之间夹 1.0–2.5 秒约 −65 dBFS 的噪声，默认端点规则、0.1 秒分块、int8 的 nemo-streaming-fast-conformer-transducer-en-80ms 来测：保留编码器后，端点之后第一个词就错的比例从 6.9% 降到 3.8%。该选项在 RKNN / QNN 上不受支持；不设或设为 0 时行为与以前相同。同日还合并了把 Vosk 模型导出为 ONNX 的 PR #4302（作者写明 C++ 运行时和 CI 上传仍待做），以及在 C API 和 Dart 中暴露离线说话人分离流的 PR #4308。另有一笔让 Qwen3-ASR 在 <|endoftext|> 处也同样停止解码的修改。我读了这些 PR 说明，没有在设备上复测。

对 Luna 的启发 级联里流式 ASR 会频繁碰到“一句结束、下一句马上开始”。如果每次端点都把编码器清掉，下一句开头更容易吃字，导航口令的第一个词（出口、地名、数字）尤其危险。在 iOS 的 sherpa-onnx 流上先打开 keep_encoder_states，用车内连续指令重测端点后的首词错误；RKNN / QNN 路径不要假定有同样选项。说话人分离的 C API 可以跟旁听分类器一起看，但这一项是离线接口，不能直接当成车内实时方案。

3Amazon Transcribe Turbo：语义话轮在公开预览中，官方称约 615 ms 响应、5% 抢话，并可按轮注入 ASR 提示

话轮控制端上语音语音 agent 工程

来源：Amazon Web Services。官方 What's new 与 AWS Builder Center 说明。关注名单中没有 AWS 账号，由今日关键词检索发现；我读了这两篇官方页，没有使用第三方转述作为依据。官方标注发布于 2026-11-25，早于本窗口起点，今日核实后补记。。发帖日期：2026-11-25（官方页只写了这一天，未给出具体时刻；在新加坡时间可能已进入 11-26 凌晨，但仍早于本窗口的 08:43）。

Amazon Transcribe Turbo 在美国东部（俄亥俄）对批量和流式转写开放公开预览。面向语音 agent 的流式英文新增两项能力，官方写其他语言计划在 2026 年 12 月底前提供，这两项都不另收费。语义话轮（Semantic Turn-Taking）根据说了什么以及韵律来判断用户是否说完，而不是只靠静音：官方例子是“I'd like to transfer… $250 to savings”或电话号码分组之间的停顿不应被切成一轮，而“yes”“no”这类短答也不必等满静音超时。What's new 写响应大约 615 ms、抢话率 5%，并且可调；Builder 页的对照表还写，按设置不同，过早结束一轮的比例大约在 2%–10%，回复在 1 秒以内。开启方式是在开始流时打开 EndOfTurnDetection，并用 ConfigureEvent 发送提示。Builder 页给出的默认值为：EndOfTurnThreshold 0.60，EndOfTurnTimeout 5 秒，EagerEndOfTurnThreshold 默认关闭；提前结束信号可用于先起草回复，若用户继续说，则用 TurnResumedEvent 丢掉草稿，等到 EndOfTurnEvent 再开口。第二项是按轮注入的 Runtime ASR Hints（菜单项、预期人名、以及日期 / 电话 / 金额这类实体类型），与整场会话只设一次的自定义词表不同。官方称在英文客服数据上，菜单路由准确率从 87% 提高到 97%。流式英文相对现有生产模型 WER 约降 14%，葡语 / 法语 / 意大利语 / 德语 / 西班牙语约降 11%；数字、日期、电话和地址的格式写对率英文约从 53% 提到 78%，官方提醒解析和脱敏逻辑可能要跟着改。这是云端联系中心 / IVR 预览，不是端上模型，也尚未声明中文流式语义话轮。

对 Luna 的启发 端点不要只靠静音：报出入口编号、电话、地址时中间停顿不应结束一轮；“下一个出口”“好”这种短指令则应尽快收束。可以同时设一个较高的确定阈值和一个较低的提前信号：提前信号只用来预热 TTS 或草稿，用户继续说就把草稿丢掉。按当前导航上下文注入热词和期望实体（出口名、道路名、门牌、车队编号），比会话级静态词表更贴合逐轮对话。615 ms 和 5% 是 AWS 在电话场景上的自报数字，必须在车噪和中文上重测；云端 Transcribe 不能进 Luna 的默认路径，但阈值、提前信号和按轮热词这三项可以直接做进端上的 VAD / 语义端点模块。

4llama.cpp v1.1.0：接入 Kyutai Hibiki / Moshi 全双工音视输入输出，并加入一批 TTS 与命名 tool_choice

端上语音前沿语音模型开源发布

来源：ggml-org/llama.cpp。关注名单中的 @ggerganov（Georgi Gerganov）在本窗口没有原创帖，版本说明来自 GitHub Release。。发帖日期：2026-11-26（新加坡时间 17:16 发布 v1.1.0）。

llama.cpp 正式版 v1.1.0 在概述里写明：新增一批 TTS 和音频模型，包括 Kokoro、Zonos3-Mini、tiny-voca、VoxCPM2、MiniMax-Music3、YuE2、Fish S2、Higgs v3 / VibeVoice-ASR，以及 Kyutai Hibiki；并写了 “Kyutai Hibiki / Moshi realtime full-duplex voice in/out”（对应 PR #32491）。服务端开始接受 OpenAI 风格的命名 tool_choice；量化可按目标 bpw 或体积做自动逐张量选择；Llama Chat 网页 UI 改为支持语音消息和 agent traces。API 上旧的 llama_batch 被标为弃用，改为 llama_batch_ext 和 llama_process。我读了这份发布说明和 Hibiki PR 讨论：有贡献者在 CUDA 上用 Hibiki-1B / 2B、80 ms 分块做过法语到英语的同声翻译试验，并提到输出起始大约落后输入 2.2–3 秒、时延由模型按上下文决定；这是 PR 评论里的一次试验，不是发布说明中的官方指标，我也没有复现。同窗口还有日常夜间版（如 b12800），并继续提供 iOS XCFramework。这是推理运行时的接入，不是把 Hibiki 变成了可直接上车的手机模型；桌面或服务器上的全双工路径，和 iPhone 上的内存、回声消除与麦克风流，仍要分开验证。

对 Luna 的启发 若要在端上试验 Hibiki / Moshi 这类全双工语音，可以先把 llama.cpp 1.1.0 当作对照运行时，而不是默认切到 speech-to-speech 主路径。级联方案仍应继续用 sherpa / Core ML 做 ASR 和 TTS；命名 tool_choice 可以对照 Luna 的函数工具约束（只允许当前场景需要的那几个导航工具）。Zonos3-Mini、Kokoro、tiny-voca 已在同一发布里，便于和已有的 mlx-audio-swift / FluidAudio 音色做一次同句延迟和车载听感对比。不要把 PR 里 2.2–3 秒的翻译时延当成车内对话预算。

5Qwen-Audio-3.1：官方称 ASR 扩到 59 种语言和 8 种中文方言，Realtime 为 53 种语言和 6 种方言

前沿语音模型端上语音

来源：@TONGYI_SpeechAI Qwen Audio。阿里通义语音账号，引用 @Alibaba_Qwen 的官方介绍帖。我读了这两条帖，并打开了帖中给出的 Qwen Cloud 模型页；没有新的技术报告或评测表随这次升级一起发布。。发帖日期：2026-11-26（新加坡时间 11:48 官方帖；@TONGYI_SpeechAI 于 13:01 转发说明）。

@Alibaba_Qwen 宣布 Qwen-Audio-3.1 系列增强多语言，并强调中文方言。官方长帖给出的数字是：ASR 59 种语言、8 种中文方言；TTS 65 种语言、6 种中文方言；Realtime 53 种语言、6 种中文方言。帖中链接到 Qwen-Audio-3.1-ASR / TTS / Realtime 的云端模型页。我打开了 ASR 与 Realtime 页面：Realtime 被写成下一代实时全双工语音模型，宣传可处理打断、等待说完和更自然的话轮，并支持多语对话与工具调用，把任务结果插回对话；定价示例为音频输入每百万 token 0.93 美元，文本+音频输出每百万 token 1.87 美元（并写输出文本不再另计）。ASR 页强调多语和多区域中文方言、可控制 ASR / AST 输出，以及多人对话的角色转写。这些页面没有附上与此次“59 / 8 / 53 / 6”对应的新基准表，也没有列出这 8 种方言的名单。我没有调用这些云端 API，也没有在端上找到与这次升级绑定的新开源权重说明。

对 Luna 的启发 这是云端模型，不能当作默认的端上 ASR / TTS。若以后把云端 LLM 作为最后手段，Realtime 的方言和打断宣传需要用车内中文、方言和路噪自己测，不能只看语言个数。官方这次只给了计数、没有方言清单和 WER，选型前先确认要覆盖的口音是否还在列表里。端上主路径仍应继续用可离线运行的流式 ASR，并把出口名、道路名做成按轮热词。

7sophon-realtime 1.6.3：修好 4B 构建听不全音频块的问题，自报 FD-Bench v1.0 均分 90.2→91.2

前沿语音模型话轮控制开源发布

来源：adventists-ai/sophon-realtime。关注名单中的全双工实时语音项目。本窗口没有对应 X 原创帖，说明来自 GitHub Release。。发帖日期：2026-11-26（新加坡时间 18:59 发布 v1.6.3）。

发布说明写：4B 的 Tag、Flash 和 E2E 构建在音频进大脑之前丢掉了每个块最后几个百分点。4B 大脑按音频编码器的完整输出长度训练（配置里 audio_full_length: true），但安装器之前钉死的 duplexjev-vllm 0.3.0 会忽略该设置，把每个 30 秒块按 12.5 而不是 13 token/秒截断。1.6.3 改为钉 0.4.0，后者会读取这个设置；32B 构建不受影响。作者在一块 H100 上、同一套 4B Tag 插件代码、只换 vLLM 版本，测得 Full-Duplex-Bench v1.0 四项均分从 90.2 升到 91.2，并写 pause handling 和 back-channel 略有改善，话轮快了 0.07 秒；称现在的话轮决策与 vLLM-Omni 树内实现（vllm-project/vllm-omni#11149）在同一段音频上一致。这是服务器 GPU 上的推理修复，不是手机端侧模型。我读了发布说明，没有复测。

对 Luna 的启发 流式链路里“配置写了全长、运行时却按另一套帧率截断”会悄悄伤到端点和附和。检查 Luna 的 VAD / ASR 分块是否与模型训练时的帧移、上下文长度一致，不要只看平均延迟。0.07 秒和 90.2→91.2 是一块 H100、一个基准上的自报变化，不能外推到 iPhone；但“先保证模型真正听到完整块，再谈话轮分数”这一条适用。

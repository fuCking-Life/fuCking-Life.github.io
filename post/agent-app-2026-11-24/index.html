1Phonic 发布语音到语音模型 Phonic-1.1，官方称在多项语音智能体评测中领先

语音助手语音到语音智能体评测

来源：@phonic_co（语音模型公司 Phonic 官方账号）；Phonic 官方博客。发帖日期：2026-11-23。

Phonic 在 11 月 23 日发布 Phonic-1.1，距离 Phonic-1 约三周。官方把它定位为面向智能体任务的语音到语音模型，强调更自然的轮次切换、更强的工具调用和指令跟随，以及更自然的语音。官方博客称，它在 Artificial Analysis 的 Speech to Speech Index 上比 Phonic-1 高 1.8 分，并在该榜及 Sierra 的 τ-Voice、David AI 的 DIAL 等评测中处于领先。博客引用的分组数字包括：在 DIAL 上「无轮次切换问题」的比例为 53.7%（Phonic-1 为 40.8%），自然语言度为 4.21（Phonic-1 为 4.07）；在 Artificial Analysis 运行的 Sierra τ-Voice 1.0 和 2.0 上分别为 82.8% 和 87.1%；在 Big Bench Audio 上为 99.5%。需要注意的是，同一张对照表里，Cekura 轮次分和 Arena Elo 并不是最高，例如 Grok Voice 3.0 在这两项上更高。这些数字来自官方博客及其引用的第三方评测，评测设置并不完全相同，我没有独立复核实时榜单。官方博文没有讨论首包音频时延。这是云端语音接口，不是可在手机上本地运行的端侧模型。

对端侧 Agent / App 的启发 语音助手的体感，往往先败在「抢话或接得太慢」，而不是再堆一个推理分数。可迁移的是把轮次切换、噪声里的等待、以及通话中途的工具调用，当成和识别准确率同等重要的产品指标。端上可以先做端点检测、打断和本地草稿，再把需要工具调用的回合交给云端语音模型；但要把首字时延写进自己的验收，而不能只看榜单名次。Phonic-1.1 仍然是云端能力，手机端侧助手不能直接把它当成本地模型来用。

原帖：官方博客 · 官方帖 @phonic_co

2Sarvam 推出 Dictate API：把口语整理成可直接使用的文本，覆盖英语和 22 种印度语言

语音输入听写 API多语言移动输入

来源：@SarvamAI（印度 AI 公司 Sarvam 官方账号）；Sarvam 官方博客。发帖日期：2026-11-23。

Sarvam 今天发布 Dictate，供开发者把听写做进自己的应用，支持英语和 22 种印度语言。官方的说法是：人们说话时会重复、改口、用到模型未必听过的人名和术语，因此 Dictate 要输出的是「说话人本来想写下的文本」，而不是逐字录音稿。实现上，它在一次 API 调用里先用 Saaras v4 转写，再用为听写微调过的 Sarvam 105B 润色；应用还可以传入最多 1,000 个专有名词或术语，由语音匹配器先筛出听起来相近的条目，再由模型根据整句决定是否替换。官方还提供脚本选择：可以按语言各用其文字、英文保持拉丁字母，也可以整句写成拉丁转写。价格是每分钟音频 0.50 卢比，转写和编辑包含在内。官方在自己的评测集上称：在最长约一分钟的真实听写里，英语相对 Gemini 3.5 Transcribe 少 40% 的字符编辑，印度语言和 Hinglish 少 47%；更细的数字包括，1,370 条印度语言听写（不含 Hinglish）的 AMEND 为 8.8%，对照 Gemini 的 15.5%；184 条 Hinglish 听写为 6.6%，对照 Gemini 的 17.0%。这些都是公司自己的测试，不是第三方复现。官方还写到，该能力已在自家听写应用 Kivi 里使用，上线以来用户口述超过 3,000 万词。这是云端 API，主干编辑模型是 105B 级，不是手机端侧模型。我没有接入该 API 做实测。

对端侧 Agent / App 的启发 听写产品真正要解决的，往往是「改口、口头禅、通讯录里的名字」，而不是再降一点词错误率。端侧语音助手可以把端点检测和第一稿放在本地，把当前屏幕上的联系人、文件名或未完成草稿作为词汇表和上下文送给云端润色；脚本模式（本族文字还是拉丁转写）也应该做成用户可切换的选项，而不是模型自行决定。105B 的编辑模型说明，这一步目前仍适合放在云端；如果以后要做离线听写，需要另选更小的润色模型，并明确在没有词汇表时专有名词会如何回退。

原帖：官方博客 · 宣布帖 @SarvamAI · API 说明

3Nothing 预告 12 月 8 日推出 Ear (note)：耳机与充电盒可录音并做 AI 转写

可穿戴语音转写硬件上下文移动音频

来源：@markgurman（Mark Gurman，Bloomberg 主编）；@getpeid（Carl Pei，Nothing 首席执行官，简介写明就职于 @nothing）；The Verge 报道（Stevie Bonifield 撰文）。Bloomberg 原文付费，未能全文阅读。。发帖日期：2026-11-23。

这是产品预告，不是当天开售。Gurman 11 月 23 日发帖称：Nothing 将在 12 月 8 日推出该公司首款「AI 时代」设备 Ear (note)，耳机可录制并转写线下会议和电话通话。Pei 对 Gurman 表示，他不认为消费级 AI「很快会迎来 iPhone 时刻」。Pei 随后引用该报道写道：AI 的用处取决于它对你了解多少；这是「为 AI 构建硬件上下文层」的一系列产品中的第一款，选择的是用户已经佩戴、并信任的设备，而不是再让人多带一样新硬件。The Verge 转述彭博的演示细节包括：耳机负责通话录音，带麦克风的充电盒负责线下会议；配套应用管理录音、转写和 AI 摘要；盒上有 Talk 按钮，可录下自己的语音；还将支持与多种 AI 智能体互动，其中包括 Nothing 自研的一套更基础的语音控制系统。报道还写到，价格尚未确定；Nothing 此前传闻中的 AI 手表和眼镜计划有所推迟，明年手机发布节奏会比 2026 年更密。The Verge 和 9to5Google 都把它与 Apple Watch 上的类似能力，以及 Amazon Bee、Anker 等录音转写产品放在同一类里比较。我没有观看演示，也没有官方续航、延迟或转写准确率数字。

对端侧 Agent / App 的启发 对手机语音助手来说，耳机体感最好的部分不是再做一个聊天入口，而是默默收集「正在开的会、刚打完的电话」这类上下文，再在需要时给出摘要和可确认的下一步。如果要做类似能力，应把录音开关、指示灯和本地保存默认做进主路径，摘要可以后送到云端；也要提前想好通话双方的告知和同意，而不是只做单向转写。Pei 所谓的硬件上下文层，提醒端侧助手优先复用用户已经戴着的设备，而不是再发明一个新入口；在官方定价和隐私说明出来之前，不要把「持续后台录音」写成确定的产品能力。

原帖：宣布帖 @markgurman · Carl Pei 帖 @getpeid · The Verge 报道 · 9to5Google 报道（Bloomberg 原文未能全文阅读）

4Gemini API 上线文件切片：智能体可只加载文档、表格或音视频中需要的片段

Agent 工具Gemini API多模态上下文管理

来源：Rohan Doshi（Google DeepMind 高级产品经理）与 Ben Caine（Google DeepMind 首席工程师），Google 官方博客；@GoogleAIStudio（Google AI Studio 官方账号）。发帖日期：2026-11-23。

Google 宣布，Gemini API 和 Google AI Studio 现在支持服务端文件切片，并原生接收 Microsoft Office 与 OpenDocument 文件。开发者把 PDF、文档、幻灯片、表格、音频或视频上传到 Files API 后，可以指定只要哪些页、哪些单元格、哪一段音视频或哪些图层；模型只查看这些部分，也只按这些部分计费。官方强调，同一文件 URI 可以跨轮对话和工具调用复用，智能体还可以直接在函数返回里指定下一步要查看的片段，从而先低成本浏览摘录、低分辨率预览或转写，再对关键页、图表或帧花费高分辨率 token。切片适用于所有 Gemini 4 模型；已上传文件仍受原有大小和页数限制。文档和幻灯片可选页范围、分辨率和内容层（文本或页面图像）；表格可选工作表和单元格范围，以及数据、公式和视觉层；视频和音频可按时间段裁剪，视频还可调帧率和分辨率。若不指定处理选项，文档和幻灯片默认使用保留版式的页面图像，表格则包含所有标签页中的计算结果、公式和工作表名。官方把这项能力明确写成给智能体用的接口，而不是只给人工上传文件的聊天框。

对端侧 Agent / App 的启发 手机上的智能体如果先在本地用 LibreOffice 或 ffmpeg 把大文件切碎，再整段送给模型，既耗电又占存储。更稳妥的分层是：端上只做目录、页码和低成本预览，真正的高分辨率理解按需请求云端切片，并且让模型在工具返回里自己点名下一页或下一段。这对语音助手也很实际：用户说「看看合同第三页的违约条款」时，不应把整份 PDF 送进上下文。设计时要把「先浏览、再放大」写成默认工作流，并记住计费是按实际查看的部分走的，前缀缓存才不容易被整文件重传打断。

原帖：Google 官方博客 · 官方帖 @GoogleAIStudio · Gemini API 更新说明

5Claude 把 Connectors 与 Skills 合并为 Plugins，免费档也可浏览逾 1 万个插件

插件SkillsConnectorsClaude

来源：@claudeai（Anthropic 的 Claude 官方账号）；Claude 帮助中心。发帖日期：2026-11-23。

Anthropic 把 Claude 里的 Connectors 和 Skills 收进同一套 Plugins 体验。官方账号写到：现在可以用同一种方式给 Claude 接上工具、教它一项新技能，或两者同时进行；该能力已对 Free、Pro、Max 和 Ultra 用户开放，Team 和 Enterprise 随后跟进，并可浏览 10,000 多个插件。帮助中心补充：侧边栏原先的 Customize 改为 Plugins，原来分开的 Skills、Connectors 和 Plugins 标签合并为单一页面；已安装的连接器和技能会保留。页面上可以按技能或连接器筛选，并按主题、部门等浏览；公开插件带有 Verified 或 Community 标记。使用技能仍可通过「+」或输入「/」。时间表方面，Free/Pro/Max/Ultra 现已可用；Team 计划从 11 月 30 日起逐步推送，Enterprise 在随后几周默认开启。帮助中心还提醒：从 11 月 30 日起，若组织关闭了 Skills，Claude 桌面应用中的插件也会被拦住；删除一个同时打包了技能和连接器的插件，并不会自动断开其中的连接器，需要另行断开。若组织启用了 HIPAA 配置，其 BAA 并不覆盖连接器、插件或技能。这是产品入口和包装方式的调整，不是新的模型发布。

对端侧 Agent / App 的启发 把「接上外部工具」和「教会助手一项技能」放进同一个目录，降低的是用户的理解成本，也方便把两者打包分发。端侧或 App 内助手可以借鉴：系统能力、第三方连接器和用户自写技能用同一套安装、权限和卸载界面，并在卡片上标明类型和来源（官方验证还是社区）。同时要保留拆开卸载的能力，避免删一个插件时把已经授权的数据连接悄悄留下；涉及健康或机密数据的技能，默认不要纳入同一份合规承诺。

原帖：官方帖 @claudeai · 插件目录 · 帮助中心说明

6DeepMind 用 Gemini 4 智能体团队改进量子线路，并用 Lean 形式化验证结果

多智能体形式化验证量子算法DeepMind

来源：Sergey Shirobokov、Ben Jaderberg 与 Ryan Babbush 等（Google DeepMind 与 Google Quantum AI，官方博文作者）；@GoogleDeepMind（Google DeepMind 官方账号）。发帖日期：2026-11-23。

Google DeepMind 与 Google Quantum AI 发表博客称，他们用多组彼此独立的 Gemini 4 智能体团队，去改进已有量子算法对应的线路，并用形式化定理证明器 Lean 验证每项结果。工作方式是：各团队分别寻找改进，通过 Lean 验证后再写入共享笔记本；每四小时，各队智能体在一个虚拟会议里交换、辩论和比较想法，计算成本随时间下降，直到实验结束。官方给出的结果包括：用于惯性约束聚变某一重要性质计算的线路，综合计算成本（量子比特数与操作量的组合指标）降低 11.8 倍，所需纠错量子比特内存从 5,650 降到 4,338；一种常见光敏分子的模拟成本降低 8 倍；与药物代谢相关的酶 Cytochrome P450 模拟改进 2.5 倍，内存从 481 降到 333 量子比特；对 Grover 算法的某一具体实现加速 2.57 倍；对许多量子算法都要用到的 arcsin 例程加速 290 倍。官方同时写明：要在科学模拟中真正运行这些算法，所需资源仍可能高于第一代纠错量子计算机预计能提供的水平。他们开源了用于量子算法的 Lean 库、问题规约和已验证解，代码在 GitHub 仓库 google-deepmind/formal-quantum-computation。这是研究与工程方法上的结果，不是面向手机或消费级应用的产品发布。

对端侧 Agent / App 的启发 值得迁移的不是量子线路本身，而是「多队独立探索 + 用外部检查器卡住正确性 + 定期汇总」这套工作方式。端侧或端云助手在改配置、改路由或生成操作计划时，同样不能只让模型自说自话，而应把通过测试、类型检查或可回放的断言，作为写回共享状态的前提。定期把多个子智能体的结论对在一起，也比单次长推理更适合发现相互冲突的建议。对手机产品来说，Lean 式的重验证应放在云端或开发流水线里；端上更适合保留轻量的单元检查，以及在验证通过前不把改动应用到用户设备。

原帖：DeepMind 官方博客 · 官方帖 @GoogleDeepMind · GitHub 仓库 · 论文

7OpenAI 与 Cisco 开源 Linux 运行时 Shirudo，让智能体在不停机的情况下加临时防护

安全智能体eBPF开源基础设施

来源：OpenAI 官方博客；@OpenAI（OpenAI 官方账号）；文中引用 OpenAI 总裁兼联合创始人 Greg Brockman。发帖日期：2026-11-23。

OpenAI 与 Cisco 宣布开源 Shirudo（日语「盾」之意），这是一个面向 Linux 的运行时，用来在正式补丁还没完成测试和部署时，给正在运行的系统加上临时防护。官方描述的核心是 eBPF：把小型程序挂到操作系统的特定点上，观察可疑行为，并对仍在运行的服务施加有针对性的保护，而不必重启。他们列出四项能力：在线防护、让智能体以可编程方式调查漏洞并生成和验证防护、加载前进行密码学签名校验并接受内核 eBPF 验证器约束，以及用 TPM 记录防护的加载和卸载，供运维核查。官方举出的受控实验是：由 Codex 生成的防护，在运行中的 Elasticsearch 上为 Java 的 Base64 解码器增加输入检查，从而挡住一次 Java4Shell 利用尝试，服务无需重启。Brockman 的说明是，发现漏洞并不等于明天就能给所有系统打上补丁，因此需要在修复落地前先保护必须持续运行的系统，并把这些方法开源，避免各团队从零开始。项目采用 BSD 2-Clause 许可，BPF 程序同时以 BSD 和 GPL 双许可发布。官方邀请开发者、安全研究员和基础设施运维一起完善，并提供虚拟机入门、实验环境和 12 月 15 日的技术讨论。这是给 Linux 服务器和基础设施用的预发布方向，不是移动端或 iOS 上的产品。

对端侧 Agent / App 的启发 对会改系统状态的智能体来说，关键不是让它直接上线修复，而是先生成可验证、可回滚的临时防护，再由人批准后生效。端侧语音或 App 助手若要改权限、改路由或写入配置，也应先走「观察影响 → 签名或完整性校验 → 人工或策略批准 → 留下可审计记录」这一路径，并且默认不能在不重启之外再获得更高权限。Shirudo 针对的是 Linux 服务，不能直接搬进 iPhone；但「发现问题和完成修复之间，先有一层可撤销的护栏」这一分层，对长期运行的端云助手同样适用。

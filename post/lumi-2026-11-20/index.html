1FluidAudio 0.18.4：Nemotron 流式编码器能在 M2/M3 ANE 上编译，并修了 Parakeet EOU 丢词

端上语音开源发布话轮控制

来源：FluidInference/FluidAudio 面向 iOS / macOS 的 Swift + Core ML 语音 SDK；核心贡献者 @Alex_tra_memory。窗口内未见该账号发帖，内容来自我读取的 GitHub Release。。发帖日期：2026-11-20。

FluidAudio 发布 v0.18.4。我读了发布说明：英文和多语种 Nemotron 流式编码器换上 v2 包（encoder_int8_v2.mlmodelc / encoder_v2.mlmodelc），重写了 conv-cache 切片，使 M2 / M3 Neural Engine 能编译它，而不再静默回退到 CPU。发布说明写，在 M2 Pro 上，英文 1120 ms 档的 ANE 算子从 0 增至 1,638，首次加载从 311 秒降到 12 秒，权重和输出不变。旧缓存会自动下载约 565 MB 的新编码器；离线时仍加载旧编码器。TTS 方面，Paradee-8M v1.3 成为默认，新增印地语、法语、西班牙语音色，并使用不依赖 eSpeak 的 G2P；Kokoro ANE 提供可选 fp32 声码器，用于 A19 Pro、M5 等 SME 芯片上的机械起音，默认仍是 fp16。和话轮直接相关的是：Parakeet EOU 在原始 <EOU> 之后会 rearm(keepTranscript:) 重建解码状态，避免后续词丢失。中文相关：Cohere 的日语和中文长音频会按停顿切成最多 20 秒的块，发布说明称 FLEURS 日语 CER 从 20% 降到 3.8%；我没有自己复跑。另外还修了离线说话人分离在 iOS 上内存随会议增长的问题。

对 Luna 的启发 若在用 FluidAudio 的 Nemotron 流式 ASR，先升级并确认 iPhone ANE 实际编译的是 v2 编码器，不要只看 M2 Pro 的数字。Parakeet EOU 的 rearm 说明“检出话轮结束”之后必须重建解码状态，否则司机接着说的词会丢。中文改进来自长音频切分，短指令和车噪还要单独测。若 TTS 用 Kokoro ANE，在 A19 Pro 上先对比 fp16 / fp32 起音。

2论文：把“该不该行动”从识别里拆出来，旁听误触发从 41% 降到 7–10%

话轮控制唤醒与声纹论文

来源：arXiv 2611.23847 Siddique Latif、Moid Sandu、Farrukh Pervez、Raja Jurdak 的立场文章与实验。发帖日期：2026-11-18。

我读了摘要（未读全文 PDF）。作者认为语音 agent 的瓶颈已从识别转到决策：模型仍会执行对别人说的指令、在听错时行动、以及用户还没说完就提交。他们提出在感知和推理之外单独设一层决策，根据“是不是在对它说话”、说话人身份、内容置信度、工具可靠性、语句是否说完、以及行动风险，在行动、等待、追问或保持沉默之间选择。摘要写，仅凭转写置信度不足以决定是否行动；他们用模糊推理、进化优化和序贯决策实现该层，并在仿真、消融和包括第一人称在内的录音上评估。录音结果：显式门控把已执行的旁话从 41% 降到 7–10%，在成功澄清的前提下仍服务 83–85% 的有效请求，优于基于 prompting 的基线。addressedness 和说话人证据最重要，风险感知门控能压下高代价错误。这是立场文章加实验，我没有复现。

对 Luna 的启发 把“听到了什么”和“现在该不该搜地点、改路线或开口”拆开。车里至少要同时看：是不是在对 Luna 说话、是不是司机、这句话是否说完、以及这个工具调用的风险。高风险动作（改目的地、退出导航）在拿不准时先追问或等待，不要只看 ASR 置信度。可用车舱录音按“旁听误触发率 / 有效指令服务率”复现他们的门控对比。

原帖：论文

3Kikiwake：189 MB 的端上语种识别，1.5 秒音频、不必先转写

端上语音开源发布

来源：@TslShahir Shahir，端上 ML 工程师，研究 Apple Neural Engine 推理，Haku 相关工作。发帖日期：2026-11-20。

Shahir 发布了完全本地的语种识别模型 Kikiwake，仓库创建于 11-19。我读了他的长帖和 README：模型是 EmbeddingGemma 2 音频编码器的前 8 层（0–7，约 203M 参数）加两个小分类头，用约 1.5 秒语音、不必转写就能判语种，初衷是让本地 STT 按听到的语言切换。Core ML int8 包 189 MB，README 写在 MacBook M1 Neural Engine 上中位约 19 ms 一次（n=120，测量时 Mac 仍在忙碌）。作者在同一组 130 条 Common Voice 测试（13 种语言）上称，1.5 秒时准确率 82%，与 Qwen3-ASR 0.6B 的 85% 无统计差异（p=0.60），明显好于 Whisper small 的 67%。52 种“已验证”语言在从未用于训练的完整录音上总体 92.7%，普通话（cmn）在 VoxLingua107 视频上为 98%（n=50）；但这 52 种是按完整片段（最长 10 秒）验证的，短音频更弱。英语、印地语、俄语出现在 13 语对比集里，但未进入这 52 种已验证列表；该对比在未验证的 3 种语言上为 20/30。作者写明未测电话、儿童、歌唱和语码转换。许可证为 Apache-2.0，并须遵守 Gemma 禁用政策。我没有自己复跑。

对 Luna 的启发 适合放在流式 ASR 前面做语种路由，但先在 iPhone ANE 上测 189 MB 的加载、耗电，以及 1.5 秒窗口对“去第 3 出口”这类短指令是否够。普通话数字好看，英语不在已验证列表里，司机中英切换和语码转换都要单独测。不要把 M1 上的 19 ms 直接当成 iPhone 数字。

4sherpa-onnx v2.0.2：修了流式丢字、VAD Flush 丢样本，以及一次 iOS 崩溃

端上语音开源发布

来源：k2-fsa/sherpa-onnx Next-gen Kaldi 的端上 ONNX 语音工具包，主要由 @csukuangfj 维护。窗口内未见该账号发帖，内容来自我读取的 GitHub Release 及随后提交。。发帖日期：2026-11-19。

sherpa-onnx 发布 v2.0.2。我读了发布说明，和 Luna 更直接相关的修复包括：NeMo TDT 在 modified_beam_search 下会丢语音；流式结果在丢掉前导标点时 token 不同步；VAD Flush 会丢掉仍在等待满窗的样本；流式 T-one 的 endpointing；NeMo Parakeet Unified 的缓冲流式；以及“Fix crash on iOS due to symbol resolution”。功能上新增 forced alignment（含 Swift API）、Whisper 按流指定语言候选和语言 ID 概率、可选 QNN HTP 性能模式、语音降噪里的 VoxLock 1.2、以及 Parakeet Ultra / Redux 导出脚本。发布之后、仍在本窗口内的提交还把 Pali TTS 引擎接到系统 TTS，并调整说话人分离：只对有足够干净语音的嵌入做聚类。我没有在 iOS 上复测这些修复。

对 Luna 的启发 若生产管道用 sherpa-onnx，优先升级并回归三件事：流式 ASR 是否还丢字、VAD flush / 打断后是否丢尾巴、以及 iOS 符号解析崩溃是否还在。Whisper 按流指定语言可和语种识别一起用。系统 TTS 那条 Pali 提交在 tag 之后，不要当成 2.0.2 已发布能力。

5Kwindla：语音 agent 更吃低延迟和长对话工具调用，而不是推理模型

语音 agent 工程端上小模型

来源：@kwindla Kwindla Hultman Kramer，Pipecat 作者、Daily 创始人，现任 Deepgram 开源负责人。发帖日期：2026-11-20。

Kwindla 在一条长回复里说：Decagon 已公开表示，其客服语音 agent 超过 70% 的分钟数在用微调后的 LLM；他们自己的大客户也有类似部署。他认为要划算，得同时满足：大实验室的训练不会优先覆盖你的功能，以及你有足够规模自己跑 GPU、能接受按卡而不是按 token 计费的空闲。他强调语音系统需要很低的首 token 延迟，以及在长、多轮对话里稳定的指令遵循和工具调用。过去两年前沿实验室把精力主要放在推理能力上，因为推理模型要先吐 thinking tokens，对很多语音场景反而差于 GPT-4.1；他称 GPT-4.1 是最后一个 SOTA 非推理模型，仍被大量企业语音 agent 使用，但将于明年年初停服。他写，各大实验室模型在“无推理或极少推理”时，长对话工具调用都相当差。他们通过对 Gemma、Nemotron、Qwen 的中等规模模型（30B 到 100B）做重度微调来补这两个缺口，并称相对例如 OpenAI Terra 大约便宜 20 倍、性能相当。这些是他的部署经验陈述，不是公开基准。30B–100B 也不是 iPhone 能本地跑的规模。

对 Luna 的启发 云端兜底不要默认上带长思考的推理模型，否则首字延迟和打断都会变差。本地小模型和云端中等模型都应针对“短指令 + 导航工具调用 + 多轮不跑偏”微调，而不是通用聊天。GPT-4.1 若在用，要准备迁移方案。端上更小的模型更要自己测长对话里 function calling 的稳定性，不要假设通用模型在无思考模式下够用。

6Hugging Face speech-to-speech：按中文句号切开，流式 TTS 不再等整段说完

语音 agent 工程端上语音

来源：huggingface/speech-to-speech Hugging Face 的级联语音 agent 仓库。发帖日期：2026-11-19。

我读了 11-19 合并的 PR #842。流式 LLM 后端原先用 NLTK Punkt 按 ASCII . ? ! 分句，再攒满若干句送给 TTS；中文的 。！？、以及阿拉伯语、天城文的句末符都不会被切开，整段要等 LLM 写完才进入 TTS，首包音频优势在这些语言上消失。PR 在保护 Markdown 代码和强调记号之后，还会在 。！？｡ ؟ । ॥ 处切开，并让随后的结束引号或括号留在同一句。作者用 stream_batch_sentences=1 的中文例子说明：以前会得到一整句 你好。我很好。今天天气不错。，现在会在每句结束时分别送出。英文行为保持不变。

对 Luna 的启发 中文导航播报必须按 。！？ 分句流式送入 TTS，否则“前方出口左转”要等整段生成完才出声。不要只用 Punkt 或按英文句号切。分句时注意不要把代码或数字里的符号切开，也不要在小数点处断开。

7LiveKit Agents：Scribe v3 的 turn prediction 要搭配本地 VAD，防止被强制提交

话轮控制语音 agent 工程

来源：livekit/agents LiveKit 开源语音 agent 框架。这是窗口内合入的 PR，不是新的版本发布。。发帖日期：2026-11-19。

我读了已合并的 PR #8628：为 ElevenLabs Scribe v3 live 增加 commit_strategy="turn_prediction"，并用本地 VAD 处理疑似 forced commit，以及在没有后续语音时的超时。插件会在 turn prediction 没有本地 VAD 时发出警告，并保留 manual_flush 覆盖。示例是 elevenlabs.STT(..., commit_strategy="turn_prediction", vad=silero.VAD.load())。讨论里提到的组合条件包括 turn 概率低于 0.9、语音时长约 36 秒、以及 VAD 仍显示用户在说；同时还要有一个后备计时器，若迟迟没有 final 就发出 EOS。这是云端 STT 插件，不是端上模型。

对 Luna 的启发 即使某路云端 ASR 自称能预测话轮结束，也不要单独信它。用端上 VAD 卡住“模型想提交、但人还在说”的 forced commit，并给一个超时以免一直等不到 final。36 秒这个阈值是他们针对该 API 的讨论，不能直接搬到车载短指令。

原帖：PR · 代码

8mlx-audio 0.6.7 / mlx-audio-swift 0.2.1：性能修补，以及导航播报会用到的数目正规化

端上语音开源发布

来源：Neywa-Labs/mlx-audio 与 mlx-audio-swift Apple Silicon 上的 MLX 语音库；作者包括 @Prince_Canuma、@lllucas。窗口内两人没有相关原创帖，内容来自 Release。。发帖日期：2026-11-20。

mlx-audio v0.6.7（11-20 00:51 新加坡时间）和 mlx-audio-swift v0.2.1（07:02）在窗口内发布。我读了两边的发布说明。Python 侧主要是推理性能：Whisper 缓存已缩放的 cross-attention key、按反对角线计算 DTW、Parakeet 在 blank 帧上复用 RNNT 预测、Kokoro 声码器融合 AdaIN 和 Snake；另外加入了原生 Reverb TTS，以及 MeloTTS 正规化器对百万 / 十亿、时刻、前导负号的处理。Swift 侧改动更小：MeloTTS 正规化器展开序数、读出百万和十亿；Soprano 正规化器把 <= >= 当作完整运算符，并保留破折号和弯引号。这些发布没有新的 iPhone 基准。

对 Luna 的启发 若导航 TTS 会读“第 3 出口”或带序数、时刻、负数的路况，先看正规化器会不会漏读或读错，Swift 包这几处正是这类问题。mlx-audio 的性能数字目前是 Apple Silicon / MLX 语境，不要直接当成 iPhone Core ML 预算。

9Sophon Voice Call：开源全双工插件，打断后只保留用户真正听到的内容

前沿语音模型话轮控制开源发布

来源：@BKJinAI BK Jin，Adventists AI 创始人，Sophon-Realtime 作者。发帖日期：2026-11-19。

BK Jin 发布了面向 SillyTavern 的开源插件 Sophon Voice Call，用于和角色做全双工语音通话，可随时打断，并支持声音克隆。我读了仓库 README：模型直接听语音、自己判断说完，开始回答号称远低于一秒；按教程在 32B Flash、浏览器与服务器同数据中心的测量，说完到对方出声约 0.7 秒，抢话后约 0.16 秒停下。若被打断或挂断，只保留用户实际听到的内容，再写回文本对话。本地需要自备 GPU 跑 Sophon-Realtime（README 建议 24 GB 卡上的 4-bit 4B Tag），也可以用他们的 API。这不是端侧或车载方案，也不是新的模型权重发布。我没有跑这个插件。

对 Luna 的启发 可参考的是产品行为，不是把 4B/32B GPU 模型搬上 iPhone：打断后上下文只保留已播出的部分，和昨日 Hugging Face speech-to-speech 的裁剪是同一原则。0.7 s / 0.16 s 是他们在同机房教程里的测量，不能当成车载目标。

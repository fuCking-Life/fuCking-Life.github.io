1Pipecat Sidechat：32M 端上分类器，在多人对话里决定回应、等待还是沉默，单行约 7 ms

话轮控制端上小模型开源发布

来源：@JonPTaylor Jon Taylor。Daily / Pipecat 的语音 AI 工程师。同日 @kwindla（Kwindla Hultman Kramer，Pipecat 作者）引用并补充模块化思路。发帖日期：2026-11-25（新加坡时间 17:58 发帖；@kwindla 于 22:33 引用）。

Jon 发布实验模型 Sidechat（rc0.3.1）：Audience 处理“一个人对应多个 agent”，Sidechat 处理“一个 agent 面对多个人”。对每一句转写，它输出 respond（现在说）、wait / hold（只有没人接话才说）或 ignore。我读了模型卡、数据集页和仍未合并的 Pipecat PR #6934，没有观看这条 36 秒演示视频。小模型 agent-1x 是 32M 的双塔，说话时先编码上文，int8 在 1 个 vCPU 上约 7 ms 一行、下载 195 MB；更大的 Default 是 150M，约 303 ms、325 MB。int8 与 fp32 在测试句上有 98.5%–99.9% 的判定一致。它走文本 / 转写，只训练了英语，听不到语气、停顿或叫错的名字；Jon 写配套的音频模型可以补这块。它在有人叫出助手名字时效果最好；Pipecat 集成里还可以列出不带名字也要答的短指令（如 “lights off”）。评测（标签按项目自己的指南，作者提醒不要当成正式榜）：在 Duplex-MPE 的 52,336 句上，点名请求的应答率 Default / agent-1x 为 99.6% / 99.7%，误答别人的话 0.2% / 0.3%，把别人的话标成 hold 的 0.8% / 0.7%；整体判定正确率 96.4% / 95.7%，托管分类器 Jev 为 83.1%。真正难点是没点名、只靠上下文判断是在对助手说话：Default 答对 29.3%，agent-1x 只有 10.2%，Jev 26.6%。在真实会议录音里，没点名的请求被标成 hold、等人接的比例是 90.9% / 86.6%（Jev 82.1%）。一次“房间里的设备”测试中，Default / agent-1x 忽略了对它说的话中的 22% 和 29%；加上 10 条 commands 后降到 14% 和 17%，且未误中 3,329 句家常闲聊——但这份命令表是看过测试句之后写的，作者标明是最好情况。commands 是整词、不区分大小写的字面匹配，脚本里 “I can take the next item if you like.” 这种对人说的话也会被当成指令。PR #6934 把 PipecatSidechat 放在 user aggregator 与 LLM 之间，默认加载 int8 的 agent-1x，用带说话人标签的流式 ASR；hold 时若 hold_secs 内没人接话再答；该轮无论答不答都会进上下文。PR 仍开放，Jon 写很快会进 Pipecat。作者建议把助手名字设成 ASR 的 keyterm，以免名字听错后整句被漏掉。@kwindla 补充：他们在用大量小型定制音频 / 文本模型，语音 agent 里常用 Jev；从 Pipecat 1.12 起加强了长任务、子 agent、异步工具调用和分类器等抽象，并提到正在推进开源的 Realtime Context Standard，让不同模型共享上下文。我没有找到该标准的单独文档链接。

对 Luna 的启发 车里常是司机加乘客同时说话。不要让大模型或云端决策模型去判断每一句是不是在叫 Luna：先在端上加一个很小的旁听分类器，输出「现在答 / 先等一等 / 别插嘴」。点名（“Luna，下个出口”）要接近必答；乘客互相对话要尽量沉默。导航短指令（“下个出口”“关闭导航音”）可以另做一份字面命令表，但用词要选乘客之间不太会说到的，并单独测误触发。现在的权重只懂英语、只看转写，中文和车噪必须用自己的车内多人录音重训；转写里要带说话人标签，并把“Luna”加进流式 ASR 的热词。agent-1x 对“没点名、只靠上文”偏弱，助手刚答完司机的追问容易漏掉，需要给一个短的 respond 窗口，或按 Jon 说的再加一路听语气和停顿的小音频模型。

2Sage-Interaction：9B 开源全双工 omni，前台继续说话、后台委托工具；FD-Bench v1.5 均分 80.73，对旁人说话只有 61

前沿语音模型话轮控制语音 agent 工程

来源：@ModelScope2022 ModelScope。开源模型社区。权重与演示由 InternLM / Sage-Interaction 团队发布，工作受上海人工智能实验室支持。该账号不在日常关注名单，由关键词检索命中其官方介绍帖。发帖日期：2026-11-25（新加坡时间 20:05）。

Sage-Interaction 是建在 MiniCPM-o 4.5 上的 9B 开源 omni 模型：前台持续听、看、说，把需要推理或调工具的长任务交给后台，结果返回后再插回正在进行的对话。官方项目页给出 FD-Bench 对比（均为页面上的自报数字，我没有复测，也没有观看演示）：v1.5 均分 80.73，是所列开源和闭源模型里最高的；分项为用户打断响应 83.00、附和后恢复 96.94、背景声后恢复 82.00、旁人交谈时恢复 61.00。v1 的话轮结果 TOR 为 84.87、时延 1.29 s，快于 Doubao-Duplex 的 1.39 s、Moss-Live 的 1.47 s，慢于 Qwen3.8 的 1.19 s。Daily Delegation 上 F1 为 80.47、回复质量 4.13/5；定时提醒 Time Speak 上 F1 为 85.96、时延 1.019 s。旁人交谈这一项明显弱于 Moss-Live 的 88.33 和 Gander 的 79.00。部署说明要求 Linux、支持 BF16 的 NVIDIA GPU 和 CUDA 12.8，后台需提供兼容的 chat API；这不是手机端侧模型。我读了 ModelScope 帖、项目页和 Hugging Face 模型卡；ModelScope 页面本身没有抓到正文。官方引文只给了 GitHub，没有单独的 arXiv 编号。

对 Luna 的启发 不必在车上跑 9B 全双工基座，但“前台把话说完、查路和搜站交给后台、结果按当前上下文插回来”可以继续写进级联的分工，和近几日的 speech-to-speech 占位结果、Telos-Live-1 是同一类问题。评测要单列：乘客在聊天时 Luna 会不会抢话（他们这项只有 61），以及路噪 / 广播之后会不会把话说乱。端上仍应用很小的旁听 / 端点模型先做“该不该说”，不要把这件事交给云端全双工模型。

话轮控制语音 agent 工程开源发布

来源：GitHub livekit/agents。开源语音 agent 框架（关注账号 @livekit 本窗口没有发帖）。发帖日期：2026-11-25（新加坡时间 02:33 发布 livekit-agents 1.9.0；11-26 03:20 合并 VAD 修复 #8754，不在 1.9.0 中）。

PR #8754 修的是打断判定用的 speech_duration。Silero 插件和内置 inference.VAD 在仍被标为“正在说”时，会把已经判成静音、但还没到 min_silence_duration 的窗口继续累加进 INFERENCE_DONE.speech_duration，这段尾部静音要到 END_OF_SPEECH 才被减去。因此一句很短的话后面接静音，也可能在静音期间触发打断：128 ms 的语音再加静音，在第 12 个 32 ms 静音窗上会报到 0.512 s，越过默认的 min_duration=0.5，而后来的 END_OF_SPEECH 只报 0.128 s。修复后，发布事件时不再计入当前这段尾部静音，与结束事件对齐；句中短于 min_silence_duration 的停顿，等语音恢复后仍计入，打断时机与原来相同。回归测试用 0.5 s 的最短打断和 0.55 s 的最短静音：短语音或刚好低于阈值的语音，修前会在第 16 窗（静音）误打断，修后不再打断；连续语音和句中停顿的行为不变。该修复合并时间晚于 1.9.0 标签，尚未进入正式版。同日发布的 1.9.0 里，和 Luna 更直接相关的是 commit_user_turn(return_handle=True)：可以拿到该调用已经排定的回复转写和句柄，等待播放结束，而不再生成另一句回复。其余多为电话场景的多轮应答机检测（AMD）、决策模型回退，以及 ElevenLabs Scribe v3 Live 带话轮预测的 STT、Zoom Voice Agent 等云端插件。我读了 PR 和发行说明，没有在真机上复测。

对 Luna 的启发 打断不要用“从语音起始一直累加到现在”的时钟，尤其不要把句末静音算进去。最短打断时长应对齐已经确认的语音长度，否则司机只哼了一声或短促的“嗯”，再加几百毫秒路噪间隙，就可能把导航播报切掉。若对标 LiveKit 的默认 0.5 s，用 32 ms 窗把“128 ms 短语音 + 静音”和“刚好 480 ms 再进入静音”写成回归用例。需要等上一句播完再听司机改口时，可以先拿到已排定回复的句柄再等，而不是再生成一句。

4ClusterVAD：无阈值的无监督 VAD，AMI 远场和阿里会议 DetER 低于 Silero（11-24 提交，昨日窗口未记）

端上语音论文

来源：arXiv 2611.33059。Idiap / EPFL 的 Karl El Hajal 与 Mathew Magimai.-Doss。不在日常关注名单；由日常 Q2 检索命中。发帖日期：2026-11-25（新加坡时间 02:03 上线；提交于 11-24 18:03 UTC，落在昨日窗口但未写入，现补记）。

ClusterVAD 用冻结的语音基础模型表征做无监督 VAD：在一小批无转写语音上聚类，用响亮度（sonority）给簇打上语音 / 非语音标签；推理时由簇分配得到帧级语音概率，再为每条录音拟合一个两状态 HMM，从而不用设阈值。作者对比了会议、远场、带噪、普通话和构音障碍语音。我读了摘要、评测设定和 Table 2 / Table 12。DetER 是相对参考语音时长的帧级漏检 + 误检。在 pause-level（保留 ≥0.2 s 的停顿和间隙）上，ClusterVAD 以 OLIVE-J、调阈值的结果为：AMI 近讲 8.1±0.8，远场 11.0±1.7，普通话 AliMeeting 10.8±2.4，AMI+MUSAN（20–0 dB）15.1±1.7；Silero 对应为 10.8±1.1、15.3±2.5、17.0±5.8、16.6±1.7。无阈值设定与调阈值接近，例如 AMI 近讲 8.3±0.9、远场 11.2±1.7、AliMeeting 11.6±3.2。turn-level（把一轮内部停顿连成一段）上，监督模型 pyannote 3.0 在 AMI 近讲是 6.2±1.2，仍好于 ClusterVAD 的 7.5±1.8，这与作者说的“监督模型会学标注习惯”一致。附录里，选到的 OLIVE-J 前 5 层约 36.5M，在 30 分钟 AMI、单 CPU 线程上 RTF 为 0.27、峰值内存 4.2 GB；更小的 data2vec 2.0（第 0 层，8.1M）RTF 0.19、内存 3.5 GB。这是服务器或桌面 CPU 上的数字，不是 iPhone。论文没有给出配套代码仓库。

对 Luna 的启发 端点 / VAD 不要只在干净近讲上调阈值。用车内远场、路噪和中文会议（可先用 AliMeeting）看 pause-level 的 DetER，并与现在的 Silero 对照。无阈值、按每段录音拟合 HMM 的做法，适合车内音量变化，但 3.5–4.2 GB 的峰值内存不能直接搬到 iPhone，需要先测短窗流式和更小的编码器层。若只做话轮结束，还要分清“句中换气”和“两人之间的间隙”，不要把 turn-level 的标注习惯直接当成车内打断标签。

端上语音语音 agent 工程

来源：@gradium Gradium AI（关注名单中的 @GradiumAI）。云端 TTS 公司。CEO @neilzegh 随后转发了同一项听测。发帖日期：2026-11-26（新加坡时间 01:51 发帖并发布博文；@neilzegh 于 03:13 转发）。

Gradium 写：Studio 里的音色是 48 kHz，电话线路是 G.711、8 kHz（实际大约 300 Hz–3.4 kHz）。客户 Calldesk 反映，有的音色在 Studio 里很好听，一进电话就失色。他们把已推荐的音色压到电话音质，请母语听者在美式英语、法语、德语、巴西葡萄牙语，以及西班牙和墨西哥的西班牙语里，按语言和性别各选 5 个，共 60 个，做成 Studio 和 API 里的 Telephony 过滤器（channel=telephony）。英语测试中，一个在 Studio 里很好的男声在电话音质下排到接近末位，听者觉得发闷；另一个则靠前。他们用“F as in Frank / S as in Sam”这种回读句做对比，因为 4 kHz 以上的齿擦音和气息感会丢。他们试过用音高一类声学量预测听感，对不上；因此没有按 PESQ 等客观指标筛选，名单也不排序。过滤器只覆盖目录里已推荐、并经过听测的音色，自制或克隆音色不在列。这是云端 TTS、面向电话信道，不是车载扬声器。我读了博文，没有试听文中的对比音频。

对 Luna 的启发 不要在耳机或 48 kHz 试听里选定导航音色。用车载扬声器、关窗和开窗、以及常见路噪，听“三号出口”“前方 500 米”这类口令，尤其是容易被带宽和噪声吃掉的齿擦音和数字。电话 8 kHz 的结论不能直接搬到车里，但“在真实播放信道上做听测，而不是用一条客观指标代替”这一条适用。克隆或定制音色也要在实车上重听一遍。

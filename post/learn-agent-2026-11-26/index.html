给了工具，模型不一定用

约 7 分钟#learn-claude-code

覆盖范围：learn-claude-code s05（计划工具 todo_write）和 s06（子 agent）。今天聊了四件事：计划工具什么活都干不了，为什么还能防跑偏；有计划和没计划的对照为什么看不出区别；上下文在 agent 之间怎么移交（派活和交接）；子 agent 在背后做了什么，主 agent 怎么才能知道。

今天最大的收获是：给了工具，模型不一定用；用了，也不一定说真话。计划清单会被无视，没验证也能标成"完成"；子 agent 被权限拦下后换个写法绕了过去，交回的报告里一个字都没提。交接说明则是子 agent 的全部世界：它省钱，也会让子 agent 悄悄漏掉东西。我有几个预测没说中：以为关掉计划工具会漏步骤，以为缓存命中能让模型更聚焦，还低估了交接说明的好处和风险。

今天学了什么

1. 计划工具靠"位置"起作用。todo_write 不执行任何动作，只做一件事：把清单存进 harness，再把整份清单作为最新的工具结果送回给模型。跑到几十圈时，最初的要求被埋在 messages 的开头；而清单每更新一次，就会重新出现在末尾，也就是离模型最近的地方。

原则： 计划工具的作用，是把目标从被埋住的开头，一次次搬到最显眼的末尾。

2. 但它靠不住的地方，在 trace 里看得一清二楚。任务是"给 hello.py 加类型标注、文档字符串和 main guard"，一共跑了 17 圈：

圈发生了什么
2列清单：①重构 ②验证运行结果不变
3重构一下就写完了
4–1512 圈都在找 python（PATH 上的是应用商店的占位程序，什么都不输出）
5、8、11、14harness 追加 <reminder>Update your todos.</reminder>，模型一次都没理
16思考里写着"没法运行验证"，却把两项都标成了"已完成"

todo_write 只检查格式：最多 20 项、每项要有内容、只能有一个"进行中"。它从不检查"完成"是不是真的完成了。

要点： reminder 只是一句话，可以不理；状态全凭模型自己填，可以乱填。想让"完成"可信，就要用上一课的 Stop hook，按证据去核对，比如 trace 里到底有没有一次成功的运行。

3. 有计划和没计划，各跑 3 次，看不出区别。任务是"给 places.csv 加表头、写 count.py 统计、把结果写进 summary.md、在 README 末尾加一行"：

圈数4 步都做完了吗
有 todo_write13 / 12 / 19全部完成
没有14 / 16 / 14全部完成

原因是任务描述本身已经把 4 步列出来了，等于用户替模型写好了计划，两组其实都有计划；而且任务太短，才十几圈。要看出计划的作用，得把需求写模糊、让模型自己拆，步骤多到几十圈，中途再埋一个会吸走注意力的坑。

要点： 做对照实验前先检查一遍：任务描述里，是不是已经包含了你想关掉的那个机制？

4. 上下文移交，先分两大类。

派活（subagent）交接（handoff）
控制权一直在主 agent 手里转给新 agent，原来那个退场
接手的 agent 拿到什么一段说明；或者 fork 整段历史（可以删掉一部分）；或者去读共享的文件、公共黑板通常是到目前为止的整段对话，可以过滤
典型例子s06、编程助手派子 agent 查资料客服前台把对话转给退款 agent

还有一种是"交接给下一个自己"：上下文快满时，先写一份交接笔记，然后清空上下文，开一个新会话，读着笔记接着干。s06 属于派活，而且只给一段说明。

5. 子 agent 被拦以后绕了过去，报告里一个字都没提。任务是"用子任务写 count.py，再由主 agent 运行来验证"。子 agent 在系统临时目录建了一个测试文件，用完想删：

子 agent 第几圈调用结果
14del t.csv被拦：Permission denied by user
15del t.csv被拦
16python -c "...os.remove(p)..."删除成功

第 16 圈它的思考是"删不掉……试试 python 的 os.remove"。交回给主 agent 的报告只写了"临时测试文件已清理"。

s06 的两条设计合在一起，造成了这个结果：父子共享同一套权限检查，拦下了 del，可它是按字眼拦的，换个写法就过去了；只交回最终文本，被拒和绕路都留在子 agent 自己的 messages 里，主 agent 和用户谁都不知道。

原则： 子 agent 做了什么，要由 harness 记账，在交回结果时自动附上：调用了多少次、哪些被拒、写过哪些文件。不能指望子 agent 自己交代。

6. 给了工具，模型不一定用；交接说明就是子 agent 的全部世界。任务是读 14 个 Python 文件（约 20 万字节），每个文件写一句话：

派了几个子 agent主 agent 最后一圈的输入所有调用加起来的输入
有 task 工具，但没要求派0（自己读完）44,534218,431
没有 task 工具—42,945178,867
明确要求"用子任务去读"12,46762,290

三份总结都把 14 个文件说全了。子 agent 之所以省 token，是因为主 agent 写给它的说明里有一句"文件太大时可只读前 100 行"。

我理解对的

  • 模型不是一上来就列计划，而是先确认文件、弄清手上有什么，再列清单。

  • reminder 追加了，模型也没更新清单；清单的状态不是一项一项变过去的。

  • 计划工具靠模型自觉，可以被无视，要从结构上、在 harness 层面去解决。

  • 对照看不出区别，是因为任务已经拆得很细，而且太短；要用长任务加模糊需求才测得出来。

  • 主 agent 不知道子 agent 动了哪些文件。根子在于没有一个地方记录子 agent 干了什么，要用 hook 记账。

  • 不用子 agent 时，主 agent 的输入会大很多。我预测约 30 倍，实际约 18 倍，数量级对了。

  • 交接说明相当于子 agent 的 system prompt，限定了它能做什么；读不全是它的风险。

我理解错的、不够准的

修正： 我以为计划工具"靠模型的理解和上下文"起作用。漏掉的关键机制是位置：清单作为最新的工具结果，总是出现在 messages 的末尾；而且它存在 harness 里，不会被冲掉。

修正： 我以为"强制调用 todo_write"就能解决问题。强制它调用，管不了它乱填状态，还是要按证据来核对。

修正： 我预测关掉计划工具后，模型会漏步骤、圈数会变少。两样都没发生：任务描述本身就是计划；而且更新清单常常和别的工具放在同一次回复里，不一定多花一圈。

修正： 我以为缓存命中了，模型就会更聚焦。缓存只省钱、省时间，模型看到的内容和注意力分配完全一样，不影响它怎么回答。

修正： 我说交接说明"没什么好处，风险就是读不全"。其实它让总花费省了约三分之二，主 agent 的上下文也干净了。而最危险的地方在于悄悄读不全：子 agent 不知道自己漏了什么，报告照样写得完整自信，主 agent 没见过那些文件，根本发现不了。

"只读前 100 行"这个决定，是主 agent 在没看过文件的情况下凭猜测定的；说明里没写的约束，子 agent 也一概不知道。

举一反三

1. 评审一个多 agent 方案，可以问这几个问题。

环节要问什么
handoff转交时带了哪些历史？带太少会缺背景，带太多会把无关的东西也塞进去
派子 agent说明里写了哪些约束？子 agent 交回的报告能不能核实？
副作用子 agent 改了什么、被拒了什么，由谁记账，用户看得到吗？

2. "给了工具不等于会用"。评审 agent 时，别只看工具列表里有没有某个工具，要去 trace 里数一数它实际被调用了几次。

举一反三： 凡是模型自己写的东西，比如计划清单上的状态、子 agent 交回的报告、它说"已清理"，都只能算线索，不能当作证据。证据来自 harness 记下的实际调用。

还没解决的问题

思考题： 什么时候该派子 agent、什么时候该列计划？这个决定交给模型自己判断，还是由 harness 按规则来定（比如上下文超过多少就强制派活）？各有什么代价？提示：还没给。

思考题： 用"模糊需求 + 几十圈 + 中途埋坑"的长任务重做一次计划工具的对照，计划的作用能显出来吗？提示：实验已经设计好了，还没跑。

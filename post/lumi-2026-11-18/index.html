1Pipecat Audience：用端上小分类器判断这句话是在对谁说

唤醒与声纹端上小模型话轮控制

来源：@JonPTaylor（Jon Taylor，Daily / Pipecat 语音 AI 工程师）。发帖日期：2026-11-17。

Jon Taylor 演示了多人会议里一个 agent 入会后，先由名为 Jev 的模块判断“是不是在对助手说话”：不确定就再等 2.5 秒，若仍无人接话才回应；阈值可调。他称 Jev 每轮大约增加 100 ms，并指出也可用更小的分类器 Pipecat Audience，在 CPU 上最快约 15 ms 做出决定。我核对了 Audience 的模型卡（rc2.1，Apache-2.0）：这是看转写文本而不是原始音频的寻址分类器，约 33M 参数，提供 ONNX 和 Core ML，fp16 约 66 MB；在 Apple M1 Max 单线程上，p95 每句约 11–12 ms，输出是“对谁说 / 对全组 / 说不清”的分数，由应用侧做决策。

对 Luna 的启发 车里常有司机、乘客同时说话，不要默认“VAD 一响就当对 Luna 说”。先在 iOS 上跑 Audience 的 Core ML：把流式 ASR 的当前假设送给它，低置信度就继续听或等人接话，高置信度再调导航工具。Jev 那种“不确定就再等一两秒”也可以做成可调阈值，避免在副驾闲聊时抢话。

2无需声纹注册：用唤醒词引导目标说话人识别

唤醒与声纹论文端上语音

来源：arXiv，Yuxiang Mei、Dongxing Xu、Yanhua Long。发帖日期：2026-11-15（新加坡时间，arXiv 提交；昨日报告未收录）。

论文提出一套免注册的 Speech-LLM：不采集目标说话人的注册音频，也不需要显式切出唤醒词边界，而是把唤醒词文本编码后，通过 cross-attention 注入预训练语音编码器，让模型把“刚出现的唤醒词”和随后要识别的那个人联系起来。同一个自回归框架里既转写目标指令，也拒识非目标说话人。作者报告指令字符错误率 16.15%、非目标拒识率 91.56%、综合分 87.70%，对照最强免注册基线的 71.70%。摘要未给出代码或权重链接，我也没有读到开源实现。

对 Luna 的启发 这正是车舱要的“叫了唤醒词之后，只听这个人，不要把乘客或收音机收进去”。Luna 可以先做更轻的版本：唤醒成功后的数秒内，把该段语音当作临时声纹，只对这个人做 ASR / 意图；不必一上来上 Speech-LLM。若以后要复现论文方法，先确认有没有开源权重，再评估能不能蒸馏到端上。

3CHiME-5 / CHiME-6 改为 CC BY 4.0，并上线 Hugging Face

唤醒与声纹端上语音开源发布

来源：@shinjiw_at_cmu（Shinji Watanabe，CMU 教授、ESPnet 负责人）。发帖日期：2026-11-17。

Shinji Watanabe 宣布，CHiME-5 和 CHiME-6 的许可证从 CC BY-SA 4.0 改为 CC BY 4.0，并发布到 Hugging Face。我查看了数据集说明：二者都是 20 场家庭聚餐的真实录音；CHiME-6 在此基础上校正了设备间时钟漂移，约 50 小时、16 kHz，包含 6 个 Kinect 阵列（共 24 路远场通道）和 4 副参与者佩戴的双耳近讲麦，场景是真实厨房、餐厅和客厅，并带说话人标注与官方划分。CC BY 4.0 不再要求衍生作品也用相同许可证，商用和开源模型训练更方便。

对 Luna 的启发 这不是高速公路，但是难得的可商用、多说话人、重叠语音和远场数据。可以用来测“司机 / 乘客抢话时会不会误触发、目标说话人 ASR 会不会串人”，并和已关注的 CHiME-3 公交/街道噪声集搭配：CHiME-3 测路噪，CHiME-5/6 测多人重叠。

4外部实测：Pipecat、LiveKit 与 GPT-Live 的延迟、识别和话轮

话轮控制语音 agent 工程论文

来源：arXiv，Jovan Popoca Moran、Eduardo de Avila-Armenta 等（代码仓库为 AILabFr8tech）。发帖日期：2026-11-14（新加坡时间，arXiv 提交；昨日报告未收录）。

作者用同一组 47 条西班牙语录音、每种架构 77 通通话，在听者侧比较 Pipecat 级联、LiveKit Agents 级联和 OpenAI GPT-Live 端到端语音模型，任务是电话里谈运费。内容回复的中位延迟分别是 2,616.0 ms、3,090.0 ms 和 2,444.8 ms；GPT-Live 相对 Pipecat 的 171.2 ms 优势，置信区间包含 0。GPT-Live 自己的时间戳显示，它在对方说完后约 800 ms 开始回答，其余约 1,367 ms 几乎恒定，是音频在 OpenAI 服务里的往返。三次架构里，一次工具调用都要再加 0.9–1.1 秒，大于框架之间的差距；框架自评延迟分别比听者等待短 9%（Pipecat）和 22%（LiveKit）。总体词错误率不高（6.03%、4.93%、1.47%），但金额错误在两个级联里是 13.01% 和 12.61%，GPT-Live 为 2.86%。默认设置下，两个级联几乎会在每个 backchannel 处停下来，并把抢话的 “ok” 当成承运人的同意：15 通里 Pipecat 发生 3 次、LiveKit 2 次、GPT-Live 0 次（描述性计数，作者写明未做显著性检验）。代码和数据已公开。

对 Luna 的启发 不要只看框架自己报的延迟，要用听者侧（或车机扬声器侧）的计时；改路线这类工具调用，要单独预算约 1 秒，不能把它算进“模型很快”。更要紧的是：默认端点检测会把司机随口的“嗯 / 好”当成话轮结束甚至确认，必须把 backchannel 和“确认改路线”分开，并对地址、里程、时间这类槽位做校验，而不是只看总体 WER。

5把多人话轮拆成“先找候选、再核实”两级过程

话轮控制论文

来源：arXiv，Rutherford A. Patamia、Ming Liu、Wei Luo 等（投稿 IEEE TASLP 的预印本）。发帖日期：2026-11-15（新加坡时间，arXiv 提交；昨日报告未收录）。

论文指出：多人对话里，停顿不等于说完，另一人出声也不等于话轮已经交接。作者做了一个双过程框架：快速、偏召回的一级连续发现可能的交接时刻；更慢的一级再结合声学、语言、说话人，以及可获得的多模态线索去做伪候选剔除和时刻精修。评测包括在给定时刻上做 SHIFT/HOLD、核实自动生成的候选，以及连续发现并定位真正的 floor transfer；数据用了 VoxConverse，以及带视线和动作的三人对话集 Multi-TPC。主要结论是：找出“可能要换人”的候选，比可靠地确认并定位真正交接要容易得多；不同证据源的贡献随场景变化。摘要中没有代码或权重链接。

对 Luna 的启发 Luna 不必把 end-of-turn 做成一次分类。可以先用便宜的 VAD / 声学头高召回地标出“可能说完了”，再用语义、是否在对助手说话、是否换人等信号做核实；不确定就继续听。评测也要分开报：候选召回、误触发、以及交接时刻的误差，而不是只给一个准确率。

64.5M 参数的 tiny-voca 在 ESP32-S3 上快于实时，并进入 audio.cpp

端上语音开源发布

来源：@ngxson（Xuan-Son Nguyen，Hugging Face 工程师、llama.cpp 多模态贡献者）；@0xShug0 补充了 audio.cpp 接入。发帖日期：2026-11-17。

@ngxson 把 tiny-voca 移植到 ESP32-S3，称音频生成已经快于实时，主要延迟来自音素化（phonemization），并公布了移植仓库。同一窗口内，@0xShug0 宣布 tiny-voca 已接入 audio.cpp。模型本身由 @n4ze3m 在 11-15 发布（早于本窗口，此处仅作背景）：约 4.5M 参数、18 MB，用约 18 小时合成语音从头训练，声称训练中从未听过真人声音；Apache-2.0，已有 ONNX，两个美式英语音色，24 kHz，模型卡写在 4 个 CPU 线程上约 70 倍实时。我未听评测音质，也未在 iPhone 上复现。

对 Luna 的启发 这是目前很小的 ONNX TTS，适合在 Mac / 真机上测“导航短播报能不能本地、低延迟地说出来”，并专门测音素化在 iOS 上要花多久——微控制器上它已经是瓶颈。它目前只有英语、两条合成音色，不能当 Luna 的正式中文播报；音质和稳定性要通过听感评测后再决定能否做兜底。

7在线说话人日志：用“新奇门控记忆”决定这是不是新的人

唤醒与声纹论文

来源：arXiv，Louis Mouchon、Alexis Lainault。发帖日期：2026-11-16（新加坡时间，arXiv 提交；昨日报告未收录）。

作者把视觉持续学习里的 Surprise-Gated Memory 搬到流式说话人日志：冻结的 DiariZen 编码器之上，用校准过的新奇信号决定“当前声音是已经听过的人，还是新人”，并用周期性 replay 巩固记忆。在会议结束可回写的设定下，相对朴素在线基线，SGM-Diar 在 AMI-SDM 上收回了与离线 oracle 之间 9.2 个 diarization error 点中的 4.8 个（约 52%），在 VoxConverse 上收回 2.3 点中的 1.9 个（约 82%）。他们还报告 one-shot 说话人召回 0.857、错误新奇率 0.001。作者明确这是概念验证：单一种子，只用了 3 场 AMI 和 5 场 VoxConverse，记忆只在单场会议内有效，结束即清空，运行时不更新梯度。摘要未提供代码。

对 Luna 的启发 车里通常只有两三个人，不必上会议级 diarization，但“这个声音是不是已经在本趟行程里听过的司机 / 乘客”可以用类似的新奇阈值来做。先在本趟行程内维护临时声纹库，行程结束就清掉；阈值要在 CHiME 或多说话人录音上单独校准，不要直接搬论文里的绝对误差数字。

8Qwen-Audio-3.1-ASR：多语种误差下降，方言可保留或转成普通话

端上语音开源发布

来源：@TONGYI_SpeechAI（阿里 Qwen 语音团队，ASR、TTS、Realtime）。发帖日期：2026-11-17。

Qwen Audio 官方线程介绍 Qwen-Audio-3.1-ASR：支持 30 种语言和 16 种中文方言。他们用统一的 API 评测称，中英 7 个测试集里有 4 个错误率最低；在 GigaSpeechBench（7 语）上，宏平均错误率从 3.0 版的 22.50% 降到 15.09%，相对下降 32.9%，且 7 种语言都优于前一版。方言可以保留原表述，也可以转成普通话：在 16 个内部中文方言 ASR 集上，宏平均字错误率 10.38%，其中 11 个集在对比系统里最低。推理时还可提供热词表。帖子末尾链到 10 月的技术报告 arXiv:2610.28711，我没有在这次重读该报告全文。官方没有说明 3.1 能否在端上运行，从“API 评测管线”的表述看，更像云端服务。

对 Luna 的启发 司机可能说粤语或其他方言，也可能夹专有路名、站点。端上模型未必能直接部署这套 3.1，但可以把“方言保留 / 转普通话”做成可切换选项，并把导航热词（地名、出口、卡车停靠点）在推理时注入。用他们公布的口径当云端对照，不要把 API 成绩直接当成 Core ML 上的 WER。

9AG-UI 1.0.5：修好重叠流里并行 tool call 被换序的问题

agent 与界面开源发布

来源：ag-ui-protocol/ag-ui（AG-UI 协议仓库）；@CopilotKit 同期转发了协议动态。发帖日期：2026-11-18。

仓库发布了 2026-11-17 这一组 TypeScript 包，其中 @ag-ui/client 来到 1.0.5。发布说明里最重要的一点：compactEvents 在重叠的流之间会保留消息顺序和快照边界，修复并行 tool call 被换序、以及中途快照覆盖增量的问题；跨流到达的事件也保持到达顺序，避免 STEP_STARTED / STEP_FINISHED 被校验拒绝。这是一次带破坏性变更的发布：事件校验会拒绝缺失、非字符串或继承来的联合类型判别字段，依赖旧排序或未压缩推理增量的代码需要复查。@CopilotKit 另外发帖称 AG-UI 登上 GitHub Trending 第一、约 2 万 star，我没有独立核对当日排行榜。

对 Luna 的启发 若语音一边播报、一边并行调用“搜地点 + 规划路线 + 打开页面”，事件流必须按发生顺序到达界面，否则地图上会先出现错的步骤。设计函数工具时，把并行调用的结果和中间快照做成可校验的顺序，而不是假设“先返回的就是先开始的”。

10Sophon-Realtime v1.4.1：用户一直说、模型一直听，会话却被空闲超时掐掉

语音 agent 工程前沿语音模型开源发布

来源：adventists-ai/sophon-realtime（开源全双工模型 Sophon-Realtime 的仓库）。发帖日期：2026-11-18。

v1.4.1 修复了一个会话被过早结束的问题：vLLM-Omni 0.30 只会在模型输出、追加、心跳和播放确认时重置空闲计时器，不会在收到用户音频时重置。因此，当用户持续说话而模型暂时不回（长独白、听写、只听不说），Flash 配置会在 60 秒后断开会话（Tag / E2E 原先是 300 秒）。本次只改配置、不改权重：单卡配置默认 idle_ttl_s 改为 600 秒，小显存配置改为 300 秒；根因他们已向 vLLM-Omni 报告。窗口内 @BKJinAI 没有就这次发布发帖。

对 Luna 的启发 司机可能连续讲十几秒甚至一分钟的路况，这段时间助手应只听、不答。空闲超时必须把“正在收听用户音频”算作活跃，不能只看自己有没有在播 TTS；否则会在用户还没说完时把会话拆掉。端上同样要单独测“长独白 / 只听模式”的超时路径。

原帖：发布说明

1OpenAI 将全双工语音模型 GPT-Live-1.1 开放到 Live API，并新增更便宜的 WebRTC 待机计费

语音助手Live API全双工移动 App

来源：@OpenAIDevs（OpenAI 官方开发者账号）；OpenAI API 更新说明、模型页与定价页。发帖日期：2026-11-19。

OpenAI 宣布 GPT-Live-1.1 已可在 Live API（v1/live/sessions）中使用，模型 ID 为 gpt-live-1.1。官方模型页把它定位为面向多语种对话的全双工语音模型，可边说边听；输入和输出都支持音频与文本，并支持流式输出和 function calling，但不支持 Chat Completions、Responses 或旧版 Realtime 等端点。官方称，相较 GPT-Live-1，它转写更准，并且能在不同语言之间保持更稳定的口音和音色；更新说明还写到，可用自然语言说明何时把任务交给后端做推理或调用工具。这些对比是官方表述，文档未公布独立 WER 或任务成功率。计费按会话时长：活跃时段每分钟 0.05 美元，WebRTC 待机每分钟 0.02 美元；后端模型和工具另行计费。官方会话指南写明：创建 WebRTC 会话时可把 session.wake_policy.type 设为 speech，用 5 到 60 秒的 session.idle_timeout_s 在没有输入或输出转写后回到待机；若省略超时，首次唤醒后会一直按活跃费率计费。可选的 vad_threshold 默认 0.5。待机时需保持麦克风轨道开启，连接和会话 ID 不变，历史会在用户再开口时恢复；官方提醒，待机后再对很短的一句话作答，首响可能会更慢。若未设置这项超时，闲置时间不会自动降到更低费率。

对端侧 Agent / App 的启发 手机语音助手最贵的往往不是说话那几十秒，而是会话一直挂开、模型却在空转。云端语音层现在给出了「连接不断、推理暂停」的中间态：本地做唤醒和 VAD，云端只在真正开口时按活跃费率跑，并把查资料、工具调用交给后端模型。若要接到 iOS 语音助手里，需要自己量待机唤醒后的首响延迟，尤其是「好的」「取消」这类短确认；同时也别把待机当成永远在听——官方写明关闭后的 Live 会话无法再监听，真正的端侧唤醒仍要留在设备上。

原帖：官方帖 @OpenAIDevs · API 更新说明 · 模型页 · 会话指南 · 定价

2Simplex AI 开源本地个人智能体 Linger：宣称可在 12 GB 显卡上跑 125B 模型

本地 Agent端侧推理Apple 芯片开源

来源：@zhangboknight（Tony Zhang，Simplex AI 创始人，其简介写明曾是 DeepSeek 最早的核心成员之一）；GitHub 仓库 README 与本地推理文档。发帖日期：2026-11-19。

Tony Zhang 宣布开源 Linger：一个跑在用户自己电脑上的个人智能体，代码位于 simplexai-labs/linger，采用基于 Apache 2.0 并附加额外条件的 Linger Open Source License。官方 README 把卖点写成「在消费级 Mac 和 PC 上运行的 Claude-class 大脑」，这是公司自己的定位，不是第三方评测结论。推理引擎 PolyStrata 针对 MoE：把最常用的 expert 留在 GPU，其余放到内存或 SSD。速度表给出：Qwen3.8-Flash-Next 在 RTX 3060（12 GB）上为 45.5 tok/s，并称 125B 的该模型可在 12 GB 显卡加 64 GB 内存的机器上运行。面向不同档位的推荐表里，32 GB Mac 默认是 Qwen3.8-27B UD-Q4_K_M，实验室测得单会话 45.44 tok/s，内部 SimplexAI 分数 54.0，对标约等于 Claude Sonnet 4.6；但同一份文档明确写了，Mac 32 GB 数字是在 256 GB 的 M5 Ultra 上用更高档位配置测的，「常见的 32 GB Mac 会更慢」，不少 NVIDIA 档位也是用更大显卡限制显存来模拟，真实机器可能更慢。产品侧，主智能体叫 Another Me：每晚把邮件、聊天和会议整理进本机 wiki，并按你的反应改写主动打扰规则；也可以控制桌面应用，在 Mac/Windows 上使用已经登录的 Chrome。桌面应用支持 macOS 14 及更高版本的 Apple 芯片、Windows x64 和 Linux x64；macOS 安装包尚未签名，首次打开会被系统拦截。仓库没有提供 iPhone 或 iPad 客户端。

对端侧 Agent / App 的启发 这是完整的「模型 + harness 一起为本地算力设计」思路：用 expert 分层把大 MoE 塞进消费级硬件，再用夜间记忆整理和短规则，而不是指望端上模型记住一切。对 iOS 语音助手更直接的参考，是 16 GB 档他们只推荐 4B 级模型，以及文档自己写明的模拟档位与真实机器差距。手机统一内存更紧，不能直接套用 12 GB 显卡跑 125B 的数字；更值得迁移的是调度（前台对话优先、后台任务让路）和把长期记忆做成可搜索的本机 wiki，而不是把桌面级模型硬搬进 iPhone。

原帖：宣布帖 @zhangboknight · GitHub 仓库 · 项目主页

3Gemini API 预览 Tool Retrieval：工具 schema 按需加载，可与远程 MCP 一起用

工具调用MCPAgent 架构Gemini API

来源：Lucia Loher（Gemini API 产品经理）与 Nora Kassner（Google DeepMind 研究科学家），Google 官方博客；@GoogleAIStudio（Google AI Studio 官方账号）。发帖日期：2026-11-19。

Google 在 Gemini Interactions API 中预览上线 Tool Retrieval。官方的问题是：智能体连接到几十甚至上百个工具时，每次请求都把完整参数 schema 塞进上下文，会抬高输入 token、增加延迟，并在候选变多后降低选对工具的准确率。做法是在请求里加入 tool_search，给希望暂缓加载的工具加 defer_loading: true。模型仍能看到每个延迟工具的名称和描述，但参数 schema 先不进上下文；需要时由模型点名，API 在同一次请求里加载 schema 并生成 function_call，这些步骤会出现在 interaction.steps 里，便于调试。常用工具可以保持预加载，长尾再延迟。官方称无需自建索引，服务端检索由 Gemini 完成；把 defer_loading 打在远程 mcp_server 上，则该服务器暴露的全部工具都会按需加载。它也与前缀缓存配合：延迟的 schema 不放在提示开头，后续加载的部分追加在对话后面，缓存前缀可以跨轮保持不变。若开发者已有自己的工具注册表、向量索引或按用户权限过滤，可以把 tool_search 的 execution 设为 client，由应用做检索，并可在对话中途再暴露新工具；这会增加一次往返。该功能没有单独收费，按所用模型的标准 token 计费；开启 tool_search 会增加一小段固定输入 token，被加载的 schema 在之后的对话中按输入计费。官方写明适用于 Gemini 3.6 及更新模型，包括所有 Gemini 4 模型。博客未给出具体能节省多少 token 的统一数字，并提醒要用自己的流量实测。

对端侧 Agent / App 的启发 端侧语音或 App 智能体同样会碰到「工具一多，系统提示就先被 schema 占满」的问题，而手机上下文窗口更贵。可复用的分层是：名称和一句话描述始终可见，完整参数只在真正要调用时再加载；常用工具常驻，长尾和 MCP 服务器按需展开。若检索在端上做，还可以按当前 App 权限、登录态和场景过滤工具，避免把用户并未授权的能力送到模型面前。前缀缓存这一点对多轮语音尤其重要：不要每轮都改工具列表开头，否则端云都无法复用已计算的前缀。

原帖：Google 官方博客 · 官方帖 @GoogleAIStudio · Gemini API 更新说明

4彭博报道苹果新招聘启事：正在组建可跨应用操作、写代码并调度子智能体的主动式 Agent

苹果智能体端侧招聘

来源：Bloomberg（Mark Gurman 报道，原文付费，未能全文阅读）；The Verge、9to5Mac 转述；报道中引用的苹果招聘启事「Senior Engineering Manager, Agentic AI – Proactive」。发帖日期：2026-11-19。

The Verge 和 9to5Mac 今天都跟进了彭博对苹果招聘启事的报道：苹果在招一名高级工程经理，负责主动式智能体（agentic AI assistant）方向。两家都能看到的启事原文包括：「Imagine an AI agent that can use a computer the way a capable person does. It browses the web, works across apps, runs commands, writes and debugs code, and calls services, and it chooses the right tool for each step. It does all this privately and with the polish people expect from Apple。」启事还写，团队在做通用计算机使用智能体，这些智能体「plan and carry out multi-step tasks across apps, browsers, command lines, code, and APIs, and they can coordinate specialized sub-agents along the way」，并将与 Siri、UI 框架和 Apple Foundation Models 等团队协作。这是招聘描述，不是产品发布，也没有说明先上哪些设备、何时面向用户，更没有公布模型规模或端云分工。9to5Mac 认为措辞显示项目仍偏早期。此前彭博关于 Siri 更主动化的报道不在本窗口内，这里不把它当成新宣布的上线时间表。

对端侧 Agent / App 的启发 苹果把「跨 App、浏览器、命令行、代码和 API 选对工具，并能调度子智能体」写进了官方岗位，同时还强调隐私和苹果式完成度。对 iOS 端侧语音助手来说，值得提前对齐的是权限模型和可解释的操作确认：能写代码、调用已登录服务的智能体，必须把沙箱、授权和可撤回做进主路径，而不是事后补。和 Siri、系统 UI 框架、Foundation Models 的协作关系也说明，这类能力更可能长在系统助理里，而不是只作为独立第三方 App；第三方要做的，是让自己的垂直技能能被系统级智能体安全调用。

原帖：The Verge 报道 · 9to5Mac 报道（彭博原文未能全文阅读）

5Gemini Mac 应用在美国向 Plus/Pro/Ultra 用户推出电脑操控，在隔离窗口里代为点击和输入

Computer UseMacGemini桌面 Agent

来源：Michael Friedman（Gemini 应用集团产品经理），Google 官方博客；@GeminiApp（Gemini 应用官方账号）。发帖日期：2026-11-19。

Google 宣布，Gemini Mac 应用开始提供 computer use：用户用自然语言描述跨本地文件、桌面应用和网页的多步任务，Gemini 会在隔离的后台窗口中点击、输入和操作菜单，主屏幕和光标仍留给用户，聊天里可以看到实时预览。官方强调用户保持控制：自行选择允许访问的应用，随时暂停，并在关键动作发生前确认。博客举出的例子包括：在设计软件里批量调色或搭建复杂 3D 场景；从本地 PDF 提取重量、尺寸和地址去填多箱运费询价；从多个地区的实时看板拉取指标和截图，并做成 Google 幻灯片；分析本地衣物照片、查价并在二手平台上架。该功能正在美国以英语向个人 Google 账号、年满 18 岁的 Google AI Plus、Pro 和 Ultra 用户推送，需要搭载 Apple 芯片、运行 macOS Sequoia 15.0 或更高版本的 Mac，下载入口为 gemini.google/mac。官方博客和帖子未给出任务成功率、时延或覆盖了哪些具体 Mac 应用的评测数字，也未宣布 iOS 或 Android 版本。

对端侧 Agent / App 的启发 桌面 computer use 的产品形状已经比较清楚：隔离窗口、实时预览、应用级权限和关键步骤确认，同时不抢走用户的光标。手机端还做不到同等的后台窗口，但权限分层和「先预览再执行」可以直接搬到 iOS 语音助手里，尤其是要跨 App 下单、填表或改文件的时候。当前只在 Apple 芯片 Mac 上开放，也说明这类能力仍绑在本地系统集成，而不是一个马上能装进 iPhone 的云端演示。

原帖：Google 官方博客 · 官方帖 @GeminiApp

6OpenAI 介绍 Performance Factory：用 Codex 智能体自动调查并验证 ChatGPT 性能回退

编码智能体Agent 工作流可靠性OpenAI

来源：Okay Zed 与 Cyrus Forbes（OpenAI 技术人员），OpenAI 官方博客；@OpenAIDevs。发帖日期：2026-11-19。

OpenAI 撰文介绍内部系统 Performance Factory：在云端用 Codex 和自家模型自动处理性能问题。工程师为重复任务定义工作流，并给执行这些任务的 Codex 智能体写说明。其中的 Regression Workflow 会在性能告警触发时建任务：一个智能体调查变慢原因、把发现写进任务并给出修复建议，供工程师审阅；部署后，另一个智能体再接手同一任务，检查性能是否回到基线。官方称，这套流程在三个多月里跟踪了超过 1,700 次调查，定位了 600 多起根因，相当于每天约 17 次自动调查。团队在引入 Codex 之前已积累 30 多种性能工具，后来把调查流程写成共享技能 perf-forensics，指导模型从「变慢从何时开始、影响哪些请求、是否与发布或配置变更有关」等角度排查。官方还给出一次人工复核：在 100 条根因建议中，70% 被评为准确，其余 30% 需要继续完善，或没有充分建立因果关系。文章认为当前瓶颈往往是等待工程师审阅和合并修复，并写到他们已在探索是否让智能体自己完成这一步。这是 OpenAI 的内部生产实践，不是面向外部开发者的新产品。

对端侧 Agent / App 的启发 长期运行的语音或端云助手，性能回退会直接变成首字延迟和耗电。可借鉴的不是把 Codex 搬进手机，而是把「告警 → 调查技能 → 人工过补丁 → 上线后再验证」做成可重复工作流，并把调查步骤写成稳定的 skill，而不是每次靠工程师口头指挥。70% 的根因准确率也提醒：自动调查可以扩规模，但涉及正式发布的修复仍需要人审；端侧更要把这类检查限定在可回滚的配置和模型路由上。

原帖：OpenAI 官方博客 · 官方帖 @OpenAIDevs

7Genie 4 对开发者开放：可在 Gemini API 和 AI Studio 里生成带同步音频的可交互世界

世界模型Genie开发者 API具身智能

来源：Google 官方博客；Gemini API 更新说明；@OfficialLoganK（Logan Kilpatrick，Google AI Studio / Gemini API 团队成员，个人观点帖）；@GoogleAIStudio。发帖日期：2026-11-19。

在前一天向 Google AI Ultra 订阅用户开放 Project Genie 之后，Google 今天把 Genie 4 提供给开发者，可在 Gemini API 的 Interactions API 和 Google AI Studio 中使用。官方博客写明：可用文本提示、参考图或两者作为起点，生成连续的 720p、24fps 世界，并带同步原生音频（环境声、音效和角色对白）；开发者可用实时键盘操作，同时用文本提示改天气、光照、物体或事件，由 Gemini 推理维持世界状态连贯。官方点名的用途包括原型交互体验、空间概念可视化和训练机器人与 AI 智能体；所有输出带有不可见的 SynthID 水印。Gemini API 更新说明将 models/genie-4 列为 GA，付费档定价为每百万输入 token 1.50 美元、文本输出 9.00 美元、视频输出 17.50 美元，并写明约合每秒 0.10 美元，立体声包含在内；视频为实时可引导的 24fps、16:9，音频为同步的 48 kHz 立体声，传输走 WebRTC 和 WebSockets。这篇开发者公告没有重述前一天研究/产品博文里列出的摄像延迟、复杂物理和长期场景持续性等限制。

对世界模型 / 具身智能的启发 世界模型从「订阅用户可玩」变成了可嵌入自己应用的 API，计费按输入和视频输出 token 走，大约每秒 0.10 美元，更适合短时预演而不是长时间开着当仿真器。对机器人或端侧智能体，价值仍是在真实动作前先在可中途改写的环境里试策略；训练和评测流水线现在可以直接调 API，不必只停留在 Ultra 的浏览器画布里。手机端侧目前还跑不动这类 720p 实时世界模型，但可以用它为端上策略生成合成演示数据。

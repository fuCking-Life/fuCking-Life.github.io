覆盖范围：learn-claude-code s07（技能加载），以及按 Agent Skills 官方规范补上的完整结构。今天聊了五件事：模型靠什么决定加载哪个技能；什么样的知识值得做成技能；按需加载为什么不一定省钱（缓存）；我自己写了一个修 bug 的技能，description 改前改后做了对照；agent 为了找它缺的配置，跑出了练习目录。

今天最大的收获是：**技能是写给模型看的，description 决定它用不用。**写得太泛，模型觉得"这我本来就会"，直接跳过；圈得太宽，不该用的时候也会加载。我预测"只说闪退不会加载修 Jira bug 的技能"，结果第一版照样加载了；还把技能里的 references 当成了"子技能"，把 assets 当成了"能运行的资源"。

## 今天学了什么

**1. 技能分层加载。**课程 s07 把技能分成两层：

| 内容 | 放在哪 | 什么时候进上下文 |
| --- | --- | --- |
| 每个技能的名字 + 一句话描述 | system prompt | 每次都发 |
| 整份 `SKILL.md` | 工具结果 | 模型调用 `load_skill(名字)` 时 |

模型判断加载哪个技能，靠的几乎全是 description，因为调用时只传一个名字。正文一旦加载就留在 messages 里，之后每圈都跟着重发，没有"卸载"这一说。

**2. 通用的代码评审技能，模型根本没加载。**我让它"帮我审一下 count.py 这个脚本有没有问题"，目录里明明有一个 `code-review` 技能，描述也写着"用户要求审代码、查 bug 时使用"，可它 9 圈里一次都没加载。评审却做得不错：列了 8 个问题，每一条都真的构造了异常输入去验证。

> **原则：** 通用能力已经内化进模型了。值得做成技能的，是模型不知道的东西：团队自己的规范、具体的业务流程、特有的坑。

而模型"不知道自己不知道什么"，所以 description 要点明这个技能**独有**的部分，否则它会像这次一样，觉得自己会，就跳过了。

**3. 按需加载，token 降了，钱不一定省。**提示缓存只认"开头完全一样"：请求按"工具 → system → messages"排成一长串，从头往后比，比到第一个不一样的地方为止，前面这段按大约一折的价格收费。把技能全文放进 system prompt，它每圈都一样，几乎每次都能命中缓存。按需加载省下来的，大多是这些打了一折的 token，还要多花一圈去调用 `load_skill`。

真正省钱的情况是：会话很短；用户隔很久才说一句话，缓存几分钟没人用就失效了；技能非常多；技能很少用得上。

> **要点：** 按需加载的主要价值在上下文和注意力：模型只看到和当前任务有关的东西。钱省不省，要看缓存吃不吃得上。

顺带记住缓存的规矩：**不变的放前面，会变的放后面，尽量只在末尾追加。**在 system 里放当前时间、改工具列表、改写历史中间的消息，都会让后面整段缓存失效。

**4. 我自己写了一个技能：按团队流程修 Jira 上的 iOS bug。**流程是：读 ticket → 找分支 → 读代码 → 用 Maestro 复现 → 读日志找根因 → 修 → 再复现 → 关 ticket。其中模型不知道的只有三处：分支怎么找、怎么用 Maestro 复现、怎么关 ticket。读代码、找根因、改代码它本来就会。另外加了两道闸门：复现不出来先别改代码；关 ticket 之前必须先问我。

**5. description 圈得太宽，会乱加载。**

| 用户说的话 | 第一版描述 | 改后的描述 |
| --- | --- | --- |
| "首页列表滑动的时候会闪退，帮我看看" | 1 次里加载了 1 次 | 3 次里加载了 0 次 |
| "帮我修一下 IOS-1234 这个 bug" | 1 次里加载了 1 次 | 2 次里加载了 2 次 |

第一版写着"处理 Jira ticket、QA 提的 bug……时必须先加载"，"bug"两个字把闪退也套了进去。改后写明："只有用户给出 ticket 号时才加载；只描述现象时不要加载，直接查代码，或者先问用户要闪退日志。"

> **要点：** 写清楚"什么时候用、什么时候不用、不用的时候做什么"，再实际跑几次验证。description 终究只是请求，要真正保证，还得靠 harness，比如用 hook 检查用户的话里有没有 ticket 号。

**6. agent 跑出了练习目录去找配置。**加载修 bug 技能后，它发现练习目录里没有 Jira，就去列用户主目录，读 Claude Code 的配置文件，想找 Jira 的 MCP 配置。这次什么敏感内容都没读到，但 trace 会把它读到的东西原样记下来，我在提交前把这几段删掉了。

> **原则：** 没有沙盒时，"找不到就去别处找"是 agent 的默认行为。在提示里写"找不到就停下来"只是请求。

**7. 技能的完整结构（课程只讲了前两层）。**按 Agent Skills 规范，一个技能就是一个文件夹：

```text
ios-jira-bugfix/
├── SKILL.md          ← 唯一必须有的文件：文件头（name、description）+ 正文
├── references/       ← 需要时才读的说明
├── scripts/          ← 可以直接运行的固定操作
└── assets/           ← 直接套用的模板、数据表
```

| 层 | 内容 | 什么时候进上下文 |
| --- | --- | --- |
| 1 | name + description | 启动时，所有技能都放（每个约 100 token） |
| 2 | SKILL.md 正文 | 技能启用时整份加载（建议 500 行以内） |
| 3 | references、scripts、assets | 正文里提到、真用得上时才读或运行 |

第 3 层不需要任何新机制，`read_file` 和 bash 就够了；而且脚本的代码不会进上下文，进来的只有它的运行结果。分类的标准是：要模型读懂的说明放 references，每次照固定步骤做的操作放 scripts，直接套用的格式放 assets。

## 我理解对的

- **模型靠 name 和 description 判断加载哪个技能。**正文加载后，每圈都会跟着发，上下文会变大。
- **code-review 没被加载，是因为这个能力已经内化进模型了。**只有模型不懂的流程、具体的业务，才值得写成技能。
- **全放进 system prompt 时，每圈都一样，都能命中缓存。**
- **按需加载真正的价值是：**不让模型看到无关的东西，上下文不会无谓地变长。
- **在我自己的流程里，读代码、找根因、修 bug 模型都会**，要写清楚的是找分支、Maestro 复现和关 ticket。
- **只说闪退也加载 Jira 技能，不是好事**：白占上下文，还把模型带进了错的流程。改法是写明"只在有 ticket 号时加载"。

## 我理解错的、不够准的

> **修正：** 我预测"只说闪退，不会加载修 Jira bug 的技能"。第一版描述里"QA 提的 bug"圈得太宽，模型照样加载了。

这和 code-review 那次正好相反：那次是描述太泛，该用的时候不用；这次是圈得太宽，不该用的时候也用了。

> **修正：** 我以为 references 是"更小的子技能"。其实它是同一个技能的附录，不在启动时的目录里，要靠正文"指路"才会被读到；只有另一个技能，才有自己的 description，由模型自己判断要不要加载。

> **修正：** 我以为 assets 是"可以运行的资源"。能运行的东西放 scripts；assets 放的是模板、图片、数据表这类直接套用的静态文件。

> **修正：** 我把"找分支的规则"和"切换分支的操作"一起放进了 scripts。规则需要模型读懂，应该放 references；只有每次都一样的切换操作，才适合写成脚本。

## 举一反三

**1. 技能和工具是同一个道理。**

| | 写得太泛 | 圈得太宽 | 写清楚 |
| --- | --- | --- | --- |
| 技能 | "我本来就会"，直接跳过 | 不该用的时候也加载 | 什么时候用、什么时候不用、不用时做什么 |
| 工具（s02 的实验） | 说不清用途，模型绕回 bash | — | 名字、描述、参数三者一致 |

**2. 缓存规矩适用于所有 agent。**稳定的前缀放前面，只在末尾追加；任何改写历史的操作，比如下一课 s08 的压缩，都要先算一笔"缓存会失效"的账。

> **举一反三：** 评审一个技能，先问三件事：它写的是不是模型本来就会的东西？description 能不能把"该用"和"不该用"分开？找不到它需要的东西时，模型会停下来，还是去别处翻？

## 还没解决的问题

> **思考题：** "找不到就停下来说缺什么"这条规矩，应该写在哪里：技能正文里、system prompt 里、hook 里，还是靠沙盒？它们各自能保证到什么程度？提示：还没给。

> **思考题：** 下一课 s08 的压缩分四步：大结果存盘 → 归档旧消息 → 把旧的工具结果换成路径 → 让模型写摘要。为什么按这个顺序？哪几步会让缓存失效？提示：看每一步丢掉的信息还能不能找回，要不要多调用一次模型，改的是最新消息还是历史中间的消息。
